# Native estimate publication contract — proposed version 1

Status: implementation-ready design for review; no publication implementation or runtime acceptance is claimed. This completes the specification for phase 1 publication and its reviewed transport boundary. Drafts, publication, client decisions and accepted-line execution remain separate layers. Phase 2 decisions and phase 3 execution are still required before the full estimate workflow is complete.

## Chosen boundary and existing evidence

Use the invoice-email preparation/capture pattern in `20260913270000_invoice_email.sql`, the authenticated Edge boundary in `supabase/functions/_shared/document-link-http.ts`, and its `document-link-runtime.ts` authentication pattern. Reuse shared bounded-body reading, escaping, exact cents formatting, SHA-256 and security headers where safe. The current invoice renderer and document-link family unions do **not** support estimate semantics; introduce an estimate-specific strict renderer and explicit transport adapters. Repository search did not identify a literal `sharedDocumentEdge` symbol; the existing `createStaffDocumentLinkHandler`/`createRetrieveDocumentLinkHandler` are the inspected equivalents.

A published artifact is captured once from a server-built snapshot and retained. Never re-render it on recovery, delivery, download, renderer deployment or contact/catalog changes. Existing invoice email payloads can be purged after 90 days; that purge policy must not govern retained estimate publication evidence. Do not reuse invoice status, money-collection links or record-release clinical consent as estimate approval.

Minimum publication artifact: one self-contained UTF-8 HTML file, at most 2 MiB, with an exact byte digest and deterministic filename. No PDF conversion service is required; browser printing is convenience, and is not the signed/approved artifact. Future PDF support adds a second independently frozen artifact and must not replace the approved HTML bytes. Store publication HTML as immutable PostgreSQL `bytea` or exact UTF-8 text with server byte digest; choose PostgreSQL for this bounded first implementation so publication and artifact identity have one transactional/restore boundary. No storage upload race, public bucket or arbitrary browser HTML capture.

## Common types and hashes

Use the canonical UUID, Money, Quantity, Fields, Draft, text limits and precise JSON rules from `draft-contract.md`. All shapes below are closed; unspecified fields are errors. Hash means lowercase 64-character SHA-256. Instant includes timezone and no more than six fractional digits. Amounts use integer strings and BigInt/numeric calculations.

- `Target = {estimate_id:UUID,client_id:UUID,pet_id:UUID}`.
- `Head = {event_id:UUID|null,version:integer>=0,record_hash:Hash|null}`. All three empty values are exactly `{event_id:null,version:0,record_hash:null}`; nonzero heads require both ID and hash.
- `Practice = {version:1,name:"The Living Room Veterinary Care",address:"2619 Spruce Street, Boulder, CO",domain:"thelivingroom.vet"}`. Freeze this server-owned versioned identity, matching the current document runtime, rather than accept a browser-controlled practice header. No invented phone number. A later practice profile/branding change must get a new explicit configuration version; historical snapshots retain version 1.
- `ClientDisplay = {id:UUID,version:positiveInt,name:string(1..301),mailing_address:string(1..1000)|null}`. A null address renders as omitted, never an invented location.
- `PatientDisplay = {id:UUID,version:positiveInt,name:string(1..150),species:string(1..100),breed:string(1..150)|null}`.
- `Artifact = {filename:string,mime_type:"text/html; charset=utf-8",byte_length:integer(1..2097152),sha256:Hash,renderer_version:1}`. Filename exactly `estimate-<estimate_id>-draft-<draft_version>-publication-<preparation_id>.html`.
- `DisplayLine = {line:Line,amount_cents:Money}` in original draft order. Allocated lines show “Allocated line total” and their real quantity; no fabricated unit price. Include pricing reasons in the document to make zero/bundle/override terms reviewable. If staff need internal-only comments later, add a separate internal field; do not silently hide the existing pricing reason.

`content_hash` is `native_fulfillment_hash(snapshot)` over the complete snapshot. `source_hash` hashes the exact preview Context below. `artifact.sha256` hashes raw UTF-8 bytes, not JSON, normalized HTML, a base64 string or text after newline conversion. Hashes with different meanings are never interchangeable.

## Preview, preparation and byte capture

`Context = {target:Target,draft:Draft,draft_record_hash:Hash,publication_head:Head,current_publication_id:UUID|null,practice:Practice,client:ClientDisplay,patient:PatientDisplay}`.

`preview_native_estimate_publication(p_estimate_id,p_client_id,p_draft_version)` returns `{version:1,actor_id:UUID,context:Context,source_hash:Hash}`. The requested version must be the current draft head. Server verifies the full immutable draft prefix and historical catalog evidence, household/patient bindings and current display rows. It rejects mismatched IDs, missing roots and malformed data. The signed quote remains the chosen draft prices: the preview does not replace them with today's catalog prices.

`PrepareRequest = {target:Target,draft_version:positiveInt,expected_source_hash:Hash,expected_publication_head:Head,replaces_publication_id:UUID|null}`. `replaces_publication_id` must exactly equal the current publication slot, including an expired current publication, or null if none. After a prior withdrawal, it is null, although the lifecycle head remains nonempty. The preview does not silently select a replacement on behalf of a stale browser.

`Snapshot = {schema_version:1,preparation_id:UUID,prepared_at:Instant,target:Target,draft_version:positiveInt,draft_record_hash:Hash,practice:Practice,client:ClientDisplay,patient:PatientDisplay,title:string,notes:string,terms:string,lines:DisplayLine[],total_cents:Money,currency:"usd",acceptance:{accept_by:string,timezone:"America/Denver",expires_at:Instant,acknowledgment_version:1,scope:"entire_exact_revision",price_validity:"accepted_quantities",not_clinical_consent:true,not_payment:true}}`.

The server computes `expires_at` as local midnight at the **start of the day after** accept_by in America/Denver; acceptance is valid strictly before that Instant. Use timezone conversion, not a fixed UTC offset or “23:59:59”. Publication must occur before it. Drafts may contain old dates, but preparation/publication rejects an already elapsed deadline. Date limits acceptance, not performance of previously accepted quantities. The displayed terms must state this explicitly. Practice approval of business wording remains a live-launch requirement, not a missing implementation branch.

`Preparation = {version:1,id:UUID,actor_id:UUID,request:PrepareRequest,request_hash:Hash,context:Context,source_hash:Hash,snapshot:Snapshot,content_hash:Hash,artifact:Artifact|null,created_at:Instant}`. The immutable preparation stores source evidence and snapshot; capture is a separate immutable row. `snapshot.prepared_at = created_at`. Preparation request hash uses `{version:1,actor_id,operation:"prepare_estimate_publication",request}`. Context/source hash exactly bind the browser-reviewed preview. Artifact is null until capture completes.

- Staff RPC `prepare_native_estimate_publication(p_id:UUID,p_request:PrepareRequest) -> Preparation` persists immutable preparation. Exact actor/request retry returns the original, even if later source facts changed; a fresh publication still rechecks eligibility. Changed same-ID input fails23514; wrong actor42501.
- Staff RPC `recover_native_estimate_preparation(p_id:UUID) -> Preparation|null` is creator-only and returns captured metadata when available. It never rebuilds content or extends expiry.
- Service-only RPC `native_estimate_capture_context(p_id:UUID,p_actor_id:UUID) -> {preparation:Preparation,captured:boolean}` verifies ownership, active actor and immutable source evidence. The actor is derived from a verified session by Edge, not an HTTP request field.
- Service-only RPC `capture_native_estimate_publication_artifact(p_id:UUID,p_actor_id:UUID,p_content_hash:Hash,p_renderer_version:1,p_html_utf8_base64:string) -> Artifact` locks the preparation's operation gate then estimate root, rechecks active actor, validates frozen snapshot/content hash and decodes bounded canonical base64/valid UTF-8. It computes byte length/digest in SQL and inserts only once. Identical byte retry returns exact artifact; different bytes fail23514. SQL validates exact renderer/version/metadata and forbidden active-content markers; the trusted Edge renderer owns full snapshot-to-HTML semantics. The staff review subsequently binds those exact bytes. Authenticated callers cannot invoke service capture directly.

Preparation and capture make **no publication** and send no messages. A stale prepared candidate can remain readable in staff history; it cannot become current without passing publish checks. Capture may finish after a draft edit, but that cannot authorize publication. Avoid holding SQL locks across an Edge renderer/network roundtrip.

### Edge contracts

`POST prepare-estimate-publication` with staff Bearer token and `{id:UUID,request:PrepareRequest}` authenticates with `auth.getUser`, calls staff preparation, then service capture context, deterministic renderer v1, capture, and staff preparation recovery. Returns `{version:1,preparation:Preparation}` with nonnull artifact only after successful capture. A retry with the same ID/request returns identical captured bytes/metadata; it never generates a new preparation ID. `POST recover-estimate-publication-preparation` body `{id:UUID}` returns `{version:1,preparation:Preparation|null}`; it may safely complete a missing capture only through the same authenticated server-render path. No request accepts HTML, practice identity, display names, prices, a service-role key or actor_id from the browser.

`POST read-estimate-publication-artifact` with staff token and `{preparation_id:UUID,client_id:UUID,expected_artifact_hash:Hash}` returns the **stored** bytes, validated against digest/length, `Content-Type: text/html; charset=utf-8`, attachment disposition with the canonical filename, and no-store/private/no-referrer/nosniff headers. Any active staff member may read an already published artifact within its exact household; an unpublished candidate is creator-only. IDs are not authorization. Staff may retain access to withdrawn/superseded artifacts as history. Missing/wrong scope is unavailable; no silent rerender fallback.

Staff SQL byte read: `read_native_estimate_publication_artifact(p_preparation_id:UUID,p_client_id:UUID,p_expected_artifact_hash:Hash) -> {artifact:Artifact,content_base64:string}` returns canonical base64 for the exact stored bytes under the same staff visibility rules; the Edge decodes and checks the digest before returning HTML.

Strict HTML uses escaped text, restrictive CSP (`default-src 'none'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'`), no scripts/forms/links/remote resources, and no active controls. The staff UI loads exact returned bytes into a sandbox with no `allow-same-origin`/scripts and displays document identity, hash, terms, expiry, price reasons and replacement impact outside the document. The artifact never claims publication happened at a timestamp that was not yet known when it was captured: label its preparation timestamp and reference; show actual publication timestamp in immutable receipt/history. The acceptance UI later identifies publication eligibility separately from immutable document wording.

## Publish, replacement and withdrawal

`PublishRequest = {target:Target,preparation_id:UUID,expected_draft_version:positiveInt,expected_publication_head:Head,expected_content_hash:Hash,expected_artifact_hash:Hash,replaces_publication_id:UUID|null,attest_document_review:true,attest_pricing_review:true,attest_terms_review:true}`.

`WithdrawRequest = {target:Target,publication_id:UUID,expected_publication_head:Head,reason:string(1..2000),attest_review:true}`.

`Publication = {id:UUID,target:Target,preparation_id:UUID,draft_version:positiveInt,draft_record_hash:Hash,content_hash:Hash,artifact:Artifact,accept_by:string,expires_at:Instant,published_by:UUID,published_at:Instant,replaces_publication_id:UUID|null}`. Publication ID equals its publish operation ID. The verified preparation owns the complete frozen Snapshot; read/history join that exact snapshot rather than duplicate and risk inconsistent content.

`Event = {id:UUID,target:Target,version:positiveInt,previous_hash:Hash|null,kind:"published"|"withdrawn",actor_id:UUID,created_at:Instant,publication_id:UUID,publication:Publication|null,reason:string|null,record_hash:Hash}`. Published events have nonnull publication and null reason; withdrawal has null publication and nonempty reason. Event ID equals operation ID. `record_hash = hash(Event minus record_hash)`. Event.previous_hash exactly binds prior lifecycle event hash. Published replacement is **one atomic event** carrying the replaced publication ID; no partially superseded state.

`Mutation = {kind:"publish",request:PublishRequest} | {kind:"withdraw",request:WithdrawRequest}`.

`Receipt = {version:1,id:UUID,actor_id:UUID,mutation:Mutation,request_hash:Hash,result:Event,created_at:Instant}`; event actor/time/ID equal receipt; request_hash hashes `{version:1,actor_id,operation:"record_estimate_publication",mutation}`. Server historical verification checks every binding and frozen evidence, not today's source state.

- `publish_native_estimate(p_id:UUID,p_request:PublishRequest) -> Receipt`.
- `withdraw_native_estimate(p_id:UUID,p_request:WithdrawRequest) -> Receipt`.
- `recover_native_estimate_publication_operation(p_id:UUID) -> Receipt|null`, creator-only. Expired/superseded/withdrawn outcomes remain recoverable; current state never replaces the original result.
- `close_native_estimate_publication_operation(p_id:UUID,p_mutation:Mutation) -> {version:1,status:"recorded",receipt:Receipt} | {version:1,status:"closed_unrecorded",closure:Closure}`. Closure `{version:1,id,actor_id,mutation,request_hash,closed_at,record_hash}`; request hash uses the exact publication mutation envelope above, record hash covers closure minus record_hash. Close acquires the same operation gate as publish/withdraw. It recovers existing matching receipt or durably tombstones the ID, so a delayed mutation cannot commit afterward. It does not withdraw a publication. Wrong actor/request rejects. No source re-review is required to close an unrecorded mutation. Capture/prepare completion cannot override a mutation tombstone.

Publish requires preparation owner = session actor, identical target and source hashes, captured bytes verified, exact latest draft version, exact lifecycle head/replacement target, and unexpired Denver deadline. Revalidate current client/patient display versions and frozen practice configuration version against preparation context after waits. A contact/name change before publication requires fresh preparation/capture/review; after publication it does not rewrite or invalidate historical bytes. Catalog changes after the saved draft do **not** rewrite the quote or force live repricing: the authoritative frozen draft has already validated exact prices/override reasons, and publication explicitly attests them. Price/quantity fields in publish requests are forbidden. All active staff retain the existing draft financial authorization policy; do not invent a DVM-only quote requirement. A future administrator approval threshold must be an explicit versioned policy checked server-side, not UI-only enforcement.

Draft saves remain independent: editing draft version N+1 after publishing N does not supersede N, invalidate its grants, cancel a decision or activate new prices. Publishing a replacement requires explicit current publication ID/head and new exact artifact review. It atomically makes the old publication unavailable for **new decisions and new accepted-line consumption**, while retaining already completed work/charges/decisions. This is a lifecycle fact for the future execution verifier; phase 1 neither creates nor transfers accepted-line quantities. Existing acceptance never approves replacement terms. New residual acceptance must explicitly account for prior usage in phase 3.

Withdrawal similarly blocks new decisions/consumption and records a reason; it does not erase a prior decision, reverse a charge, cancel performed treatment or create a refund. If no currently active publication matches, return40001 and require fresh review. Repeated exact mutation ID returns its receipt.

## Locking, authorization and failure behavior

One shared root gate: `pg_advisory_xact_lock(hashtextextended('native-estimate:' || estimate_id::text,0))`, identical to draft save. All state mutation acquires its **own operation UUID** gate first (`hashtextextended(p_id::text,0)`), then this root gate. Preparation/capture uses the preparation UUID gate. Publish must not additionally acquire a preparation UUID gate after root acquisition: captures also need root, and this would invert order. Root serialization plus immutable capture rows is sufficient; if capture has not committed, publication fails as not-ready and cannot report success. No lock upgrade requiring another operation UUID while holding root.

After root waits recheck active staff, exact root/client/patient identity, required draft/lifecycle heads, availability and expiry. Lock client then patient display rows FOR SHARE as in draft save when computing/rechecking current publication source. All publication/withdrawal/decision/accepted execution paths must use this root namespace before changing lifecycle-dependent state. No provider call is made inside a transaction. Publish/withdraw mutation closure checks run under their operation gates. Preparations have no publication authority and need no mutation tombstone merely to discard a preview; a pending publication mutation must still be resolved before replacing it.

Use `clock_timestamp()` after waits for expiry and publication/withdrawal/closure timestamps, never transaction-start `now()` to let a waited-out request publish after deadline. Preserve nondecreasing lifecycle timestamps. SQLSTATE40001 for stale reviewed heads/source,23514 for malformed/changed identity and closed IDs,42501 for authorization. Historical recovery validates evidence and creator even when current source is stale; it does not re-run publish eligibility.

Null recovery proves only absent committed receipt at that read. The browser retains the original UUID/mutation across uncertain replies/reload, can retry only the identical request, and unlocks replacement only after exact validated receipt or serialized closure. Late responses cannot clear another actor/household's pending request. Prepared document previews are distinct from pending publication mutations in session storage.

## Reads and explicit completeness

`read_native_estimate_publication(p_estimate_id,p_client_id)` returns `{version:1,actor_id:UUID,target:Target,head:Head,current:Publication|null,current_status:"none"|"open"|"expired"|"withdrawn",latest_publication:Publication|null}`. `current` is the last published revision only while not withdrawn; an expired one remains current but is unavailable for decisions, so status is expired. Withdrawn returns current:null and retains latest_publication for history. Superseded is a status of older publications, never the current slot. Missing root is23514; wrong household is23514. `none` means no publication event, not missing data.

`read_native_estimate_publication_history(p_estimate_id,p_client_id,p_before_version:null|positiveInt,p_limit:1..100)` returns `{version:1,actor_id,target,head,events:Event[],has_more:boolean,next_before_version:null|positiveInt}` newest first, limit+1 and exact cursor. Arbitrary positive before-version cursors are valid upper bounds. Every emitted event/publication is verified; no silent100-event truncation. A staff detail RPC `read_native_estimate_published_revision(p_publication_id,p_client_id)` returns `{version:1,actor_id,publication:Publication,snapshot:Snapshot,head:Head,status:"open"|"expired"|"withdrawn"|"superseded"}` with retained bytes accessible separately. Future decision history is an additional paginated ledger, never inferred from document delivery events.

## Read-only delivery and future decision boundary

Phase 1 includes reviewed document delivery through an explicit `estimate_publication` source family adapter, **not** immediate client decision capabilities. Reuse existing SMS/document-link grants and email outbox lease/exact payload patterns only after extending their closed family validators, source context, artifact selection, worker routing, redaction and restore tests end to end. Never masquerade an estimate as an invoice or record release. Source_id = publication ID; source_hash binds `{publication_id,content_hash,artifact_sha256}`. The adapter reads stored publication bytes and cannot call the renderer. Recipient/channel/subject/body are a separately prepared, captured and reviewed transport request with exact payload hash; retries return exact grant/outbox receipt, not a new send. Delivery commissioning/provider gates remain enforced; synthetic tests do not send external messages.

### Exact delivery adapter surface

For SMS, reuse `prepare-document-link` with its existing closed body `{p_request_id,p_family:"estimate_publication",p_source_id:publication_id,p_client_id,p_conversation_id,p_recipient,p_source_hash,p_expires_at,p_message_template}` and existing recovery/enqueue/revoke contracts. All fields retain their existing validated types and semantics. Add a new explicit estimate-publication branch to each SQL/Edge/worker family dispatch; the source bundle is `{publication:Publication,snapshot:Snapshot,artifact:Artifact}`. The artifact builder downloads the captured bytes through a private service RPC; it must not hand this source to `renderInvoiceDocument`. The grant's report hash/manifest must equal the publication's exact HTML digest/length; capability URLs are placed only in the separately captured message payload, never injected into approved HTML. The existing original-attachment list is empty for this family.

For email, add an estimate-specific wrapper matching the existing invoice-email durable flow:

- `EmailRequest = {publication_id:UUID,client_id:UUID,conversation_id:UUID,recipient:string,subject:string(1..200),body:string(1..10000),expected_source_hash:Hash,expected_artifact_hash:Hash}`. Normalize/validate recipients using the existing communication recipient helper, preserve the exact reviewed normalized request, bind conversation household, and keep provider sender/reply-to under existing server settings.
- `prepare_native_estimate_email(p_id:UUID,p_request:EmailRequest) -> EmailPreparation`, `recover_native_estimate_email(p_id:UUID) -> EmailPreparation|null`; creator-only exact requests, where `EmailPreparation = {version:1,id:UUID,actor_id:UUID,request:EmailRequest,request_hash:Hash,source_bundle:{publication:Publication,snapshot:Snapshot,artifact:Artifact},created_at:Instant,payload_hash:Hash|null,manifest:Artifact[]|null,outbox_id:UUID|null}`. Request hash uses `{version:1,actor_id,operation:"prepare_estimate_email",request}`. Exactly one manifest entry is permitted and must equal the published artifact. Never allow a caller to name another attachment/bucket/path.
- Edge `POST prepare-estimate-email` body `{id:UUID,request:EmailRequest}` uses staff authentication, prepares, gets service-only `native_estimate_email_capture_context(p_id,p_actor_id)`, constructs the ordinary Resend-compatible envelope from frozen message and **stored** artifact bytes, then calls service-only `capture_native_estimate_email_payload(p_id,p_actor_id,p_payload_text)`. Capture validates exact recipient/subject/body/sender-policy, canonical one-attachment metadata, decoded bytes and publication digest before insertion. Its digest covers exact provider payload text. Return `{version:1,preparation:EmailPreparation}`. Capture retries may only supply identical text; recovery never re-renders or swaps bytes/sender configuration.
- `enqueue_native_estimate_email(p_id:UUID,p_reviewed_payload_hash:Hash,p_attest:true) -> {version:1,request_id:UUID,outbox_id:UUID,payload_hash:Hash}` appends exactly one existing `communication_outbox` row under the existing durable request link. Recheck active creator, captured hash, publication eligibility and recipient/conversation scope after waits. No provider call occurs here. Exact retry returns the same outbox identity even if subsequent delivery state changes.
- Existing worker `read_reviewed_communication_payload(p_outbox_id,p_lease_token)` dispatch gains `artifact_kind:"estimate_publication"`; workers use frozen payload under the established lease and idempotency key, never rebuild it. No generic fallback may omit artifact verification.

Delivery preparation/queue/revocation locks use their own request/grant gate before the estimate root gate, then any existing outbox/grant row locks. Retrieval needing both root and grant locks follows root→grant and no reverse acquisition. Publication replacement/withdrawal need not eagerly update every grant: effective eligibility derives from the serialized root lifecycle, preventing a root↔grant fan-out deadlock. Before implementation, verify these orders against the actual shared grant/outbox RPCs and add observed wait tests; do not nest a shared helper with the opposite order.

The existing enqueue idempotency is safe to retry; an absent recovery still cannot justify a replacement send while an earlier enqueue may finish. Provide `close_native_estimate_email(p_id,p_request)` with the same serialized recorded-versus-closed pattern as publication mutations: if already linked, return the immutable enqueue identity, otherwise tombstone the request so a delayed enqueue is rejected. Capture may remain as evidence. Lost delivery replies must resolve the same request ID rather than create a duplicate message. Shared SMS grant flow retains its existing durable close/revoke recovery semantics and must be tested for this new family.

Existing document-link API shapes remain unchanged except explicitly accepting the new family where supported. Grant client_id must equal publication client_id; grant issuance and enqueue require an active publication and active staff after root/grant waits. Existing granted views must check effective supersession/withdrawal at retrieval; staff historical access remains. Expired estimate acceptance and grant expiry are distinct: an unrevoked read-only grant may continue displaying an expired quote with an explicit expired badge; it cannot accept it. Grant expiry is independently bounded by existing transport policy.

Revoking or rotating a lost read-only delivery grant affects that grant only. It does not withdraw/supersede publication, change financial terms or cancel any accepted plan. Conversely withdrawal/replacement blocks new decision/consumption even if a prior token still exists. Public rendering identifies status outside the retained HTML, so status badges do not mutate approved bytes.

Phase 2 must add a **separate domain-separated decision grant and endpoint**, bound to publication ID, artifact SHA-256, household/patient, expected lifecycle head, acknowledgment version and acceptance deadline. No extension of a read-only bearer link may silently confer signing rights. Client identity is possession of the grant plus self-reported signer details, not authenticated identity proof. This design reserves that boundary but exposes no fake accept/decline buttons until its SQL/HTTP/browser/race tests exist.

## Why publication is not consent, payment or execution

The document proposes a price and scope. Its approval later authorizes only the exact commercial proposal, not anesthesia consent, surgery consent, prescribing, clinical appropriateness, a card charge or medication availability. Publication itself creates no invoice, invoice item, treatment, dispense, stock movement, allowance consumption, payment request, accepted-line authorization or communication outbox row. Sending occurs only through separate reviewed delivery. Phase 3 will atomically link actual performed work to the accepted immutable line and consume its remaining quantities/allocated cents once; publish/replace must never activate that path by implication.

## Required acceptance before declaring phase 1 publication complete

- SQL and strict-adapter parity for closed objects, exact price inputs/totals, frozen catalog evidence, date boundaries/DST, source/hash/artifact mismatches and actor/household/patient scope.
- Staff browser prepare→capture→read exact bytes→review→publish, continuing draft edits, explicit replacement and withdrawal, paginated history and historical byte download.
- Actual Auth/Edge tests: renderer escaping/CSP, no browser HTML capture, service-only capture, malformed/oversize bytes, duplicate identical/different capture, recovery after renderer deployment and real digest verification.
- Observed contention: draft edit versus publish, source display change versus publish, capture versus publish, competing replacement/withdrawal, staff revoked while waiting, deadline expiring while blocked, both orders/rollbacks of publication versus close.
- Lost prepare/capture/publish/withdraw/close responses, persisted original mutation across reload, no unsafe unlock on null or malformed responses.
- Reviewed email/SMS delivery source adapter, immutable byte selection, grant revocation separate from withdrawal, exact worker payload routing and zero external dispatch in synthetic acceptance.
- Populated restore preserves preparation, bytes, hashes, full revision/lifecycle/operation/closure chains and grant/outbox attribution; verifiers reject corrupted historical data without comparing against today's catalog.
- Public client approval and actual accepted-line execution remain explicitly unfinished until their subsequent phases pass independently.
