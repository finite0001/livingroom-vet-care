## Phase1: immutable scope, child binding and recovery

Create `ezyvet_migration_runs` with caller-generated request UUID, server-derived `actor_id`, source origin/site, canonical request hash, scope manifest hash and creation timestamp. Store scope rows separately in `ezyvet_migration_scopes`, with stable scope UUID, approved animal/contact mapping references, local household/patient identity, resource and explicit supported parent identity. Use normalized rows for foreign keys and uniqueness, not a mutable opaque JSON job description. Canonical ordered JSON is the request/report hash representation.

Scope is immutable after creation. A changed patient/site/resource selection creates a new request, optionally linked to its predecessor; exact retry returns the original. Represent required resources, explicit exclusions with reasons, and unsupported requested scopes distinctly. Unsupported contracts cannot acquire a child run or count as migrated. Contact/animal identity scope refers to exact approved mapping and source versions; generic scans are not assumed patient-scoped.

Create append-only `ezyvet_migration_bindings` connecting scope UUID to existing `ezyvet_import_runs.id` plus validated resource-specific context. Multiple attempts are historical bindings; an explicit replacement identifies the preceding binding and reason. Never rewrite the child cursor, lease, requested_by, cooldown, page ledger or source context. Exact binding UUID retry returns the same record; a changed binding payload fails. A child cannot be attached to mismatched site, actor, patient, resource or parent. Enforce unique `(scope_id, child_run_id)` binding and exact operation UUID recovery. The same child may be referenced by different explicitly reviewed manifests; reference membership grants no new continuation authority. Distinct-child/observation totals deduplicate across scope references. Generic contact/animal runs contribute only manifest-selected exact source identities, never every item from an unscoped scan. Do not manufacture actor handoff; another administrator creates a separately owned run until an explicit audited transfer contract exists.

Initial RPCs: `prepare_ezyvet_migration_run`, `read_ezyvet_migration_run`, `list_ezyvet_migration_runs`, `bind_ezyvet_migration_child`. Each uses `auth.uid()` and active ADMIN checks; all reads and writes are actor-scoped. Staff/anonymous/service direct table grants are denied, with RLS enabled and explicit PUBLIC function revocation. Recheck role/ownership after any wait before mutation or returning private recovery data. List by `(created_at,id)` keyset cursor, bounded20/default and100/maximum with sentinel; validate cursor pair together.

Acquire only a migration-request advisory lock for request idempotency, followed by the run/scope rows in deterministic UUID order. Do not hold source/parent locks while invoking existing child claim functions. Validate immutable child ownership/scope identity without acquiring child/source/mapping locks. Capture historical membership even if its observed source is now stale; expose staleness explicitly and let the existing continuation/review APIs enforce current eligibility. A binding performs no provider request. A consistent mutable-state report is a separate contract below, not a side effect of binding.

Acceptance: exact create/recovery after lost reply; changed same UUID rejected; two simultaneous creates bind one immutable manifest; cross-actor/site/patient/parent/resource binding denied; stale historical evidence remains readable/bindable by exact immutable identity but cannot become current or authorize continuation; role revoked during observed wait denied; canceled/changed child context remains visible rather than silently replaced; no child/provider/clinical/stock/invoice/outbox side effects; raw table access denied; server history survives lost local pointer.

## Phase2: truthful counts, discrepancies and report evidence

Create a read projection over existing ledgers, keyed by migration scope and exact observation identity. Report **occurrences** (run/page/ordinal where available), **distinct source identities**, **distinct snapshot versions**, and **reviewed local outcomes** separately. Source identity includes origin/site/resource/external ID; original capture also includes canonical parent/metadata/file identity. Never sum a cross-page duplicate twice as a distinct identity or count one source version as two approved clinical records.

Show lifecycle facets rather than a misleading additive total: observed/staged counts; pending review; exact current approved or linked outcome; rejected/excluded with reason; stale/superseded; unresolved reference/coverage gap; attempt failure/cooldown. Explain overlapping metrics. A retry failure belongs to an attempt, not a fabricated source item. The generic import run stores only `last_error_code` and retry time, not append-only failure history. Add narrow append-only attempt events at canonical claim/failure/stage boundaries for bound child runs, keyed by child/lease/event identity and emitted in the same transaction. Replays must not duplicate events. Do not infer a complete pre-binding attempt history; mark it unavailable and retain the observed baseline error separately. Keep event payloads redacted and never log provider tokens or arbitrary source URLs. A failed page has unknown unseen contents, not zero missing records. Unknown provider totals remain unknown.

Per-resource adapters must join exact snapshot/head/review versions and local provenance. Never infer approval from generic `proposed_match` or raw staging alone. `review_ready` is scan traversal state; `page_limit_reached`, pending pages, stale mapping/head, unresolved joins and unverified original bytes remain explicit blockers. Prescription item reconciliation retains explicit partial/missing-item disclosure; attachment byte approval/cancellation uses canonical record versions and captures. Native local edits are never overwritten by reconciliation.

Create append-only `ezyvet_migration_resolutions` for operational dispositions with reason, actor, exact evidence hash and predecessor. These do not perform clinical review, prescribe, sign, promote data, approve a vaccine certificate or dismiss source discrepancies in their existing clinical ledger. Link to the correct native review flow when clinical action is needed. Excluding a required scope does not erase it or establish a full migration; acceptance must disclose every approved exclusion and unsupported scope.

Add paginated `list_ezyvet_migration_items` and summary/detail RPCs, plus idempotent resolution requests. Persist `ezyvet_migration_report_requests` and immutable reports containing manifest/version, scope/binding IDs, observation/review/capture identity digests, explicit missing/failed/excluded coverage, source cutoff semantics and prior-report reference. Bound report generation by scope/page limits and explicit continuation; do not silently truncate a report. A final seal verifies that every planned chunk belongs to the same report inputs; changes require a new reviewed report. Persist only source references and necessary summaries, not redundant medical payloads or secrets.

Report acceptance rechecks actor, current evidence and exact reviewed hash after waits. Keep accepted evidence immutable and expose later currentness separately. Separate `report reviewed` from `migration accepted for cutover`: the latter additionally requires the recorded supported-source/export strategy, coverage exceptions, owner scope decision and clinical acceptance. Do not implement a green global complete badge based on empty local queues.

Acceptance: duplicate observations; several snapshots of one source; superseded/canceled approval; missing consult/product/prescriber/item; failed/unfinished/page-limited scans; zero observed records with no accepted completeness evidence; source changes during report preparation/acceptance; exclusion cannot hide required scope; local edits preserved; exact retry and immutable report; no unintended data promotion or deletion.
