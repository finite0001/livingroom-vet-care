## Atomic dispatch and ambiguous outcomes

Use two independent guards: an exclusive local run receipt (`O_EXCL`, mode 0600) that prohibits a restarted runner from resuming, and a durable server-side one-shot marker per reviewed ticket/case. Before dispatch, create its exact object with `x-upsert:false`; only an unequivocally successful creation permits one provider `fetch`. Concurrent invocations race on this same object; a duplicate, timeout, unknown guard result or lost guard acknowledgement never dispatches. Set the in-memory dispatch count before `fetch`; all outcomes consume the case permanently. Do not rely on provider idempotency headers as a substitute for this guard.

Persist a local `may_have_dispatched` journal entry and reserve the full worst-case case budget before calling the probe. A lost probe acknowledgement means **possibly billed**, never zero cost. A process restart, timeout, rate limit, 5xx, refusal, malformed response, truncated body or lost receipt cannot trigger replay. Stop remaining cases on uncertain dispatch/billing, changed fixed inputs/flags or failed attestation; leave their states explicitly `not_attempted`. A later user-authorized new evaluation is a new budget and ticket, not recovery of a spent case. The guarantee is for this fixed runner/probe and reviewed ticket; an administrator deliberately replacing code/guards is outside that boundary.

Do not remove one-shot markers while any matching probe may still execute. Disable/delete owned functions first and verify absence; retain guards if deletion is uncertain. Retain guards through the fixed expiry plus bounded in-flight timeout before deleting them. Expiry is embedded in the reviewed sources, never extended during cleanup. Cleanup retries may remove resources or retrieve already retained evidence; they may never repeat generation.

## Evidence and frozen-import bridge

For every case retain status `not_attempted`, `guard_refused`, `dispatch_uncertain`, `response_partial` or `response_complete`; possible versus confirmed dispatch counts; exact request and bundle hashes; provider HTTP status and supplied request ID; raw response bytes/prefix in canonical base64 and a raw-byte SHA256; body-completeness/truncation flags; times; returned model/status/usage when safely parseable; and parser result/failure. Never infer zero provider cost from missing usage. Never discard failures from totals.

Collect bytes before UTF8 decoding/JSON parsing. Keep the production **512000-byte** response limit: an overflow retains the bounded prefix, is explicitly incomplete, cancels the reader and cannot pass. A midstream failure retains every observed byte. A lost outer probe acknowledgement retains any observed outer-response prefix plus `dispatch_uncertain`; do not claim provider bytes were preserved if they were never received locally. A complete proof cannot be asserted when that evidence is unavailable.

The current `lrv-call-fidelity-raw-v1` importer has no body-completeness field, so only a provably complete upstream body becomes `{kind:"http",status,request_id,raw_body_base64}`. Partial/uncertain/guard-refused/not-attempted cases become an explicit `{kind:"transport_error",error}` referencing their private sidecar receipt and byte hashes; preserve those sidecars with the review packet. **Never pass a potentially valid-looking JSON prefix as a complete HTTP body.** Refusals, non-2xx and malformed but complete bodies remain complete HTTP outcomes and fail the existing production parser as appropriate.

Use the unchanged offline CLI to generate JSON/Markdown and pending adjudication. An imported-output hash binds supplied bytes, not provider authorship. Structural validity and provider completion do not establish clinical fidelity. ## Dollar admission versus a guaranteed billing cap

**A dollar ceiling is not yet calculated or authorized.** Ten requests, an 8000-token output ceiling and a dollar budget alert do not by themselves establish a cash limit. Define whether D covers OpenAI usage only; any temporary Supabase execution/storage charges must be separately disclosed and bounded or included in the authorization, never silently treated as free.

Before approval, verify official prices for this exact model/account/endpoint and access to this alias; retain source URL/date and applicable billing tier. Verify how input, cached input, reasoning/output and any other billable components are metered, and that `max_output_tokens` actually bounds every billable output category. Obtain a documented conservative bound for each exact input, including schema/message overhead, with the supported tokenizer or a provider-guaranteed equivalent. If any billable component or price cannot be bounded, fail preflight rather than invent a price or token conversion. No extra counting/probing API request is authorized implicitly.

For verified upper bounds, calculate each `W_case` using the highest applicable uncached input/output rates and documented extra components; assume no cache discount and count every uncertain dispatch at its full reservation. Require `sum(W_case) <= D` for the user-selected ceiling **D**, with explicit safety margin and currency/rounding rules. Freeze those rates and assumptions in the reviewed plan. The serial runner admits a request only after permanently reserving its full `W_case`; it never refunds a timeout or admits extra cases from optimistic observed usage. This enforces the application's **calculated admission budget under those pricing/metering assumptions**, not an unconditional promise about the provider's final bill or shared-account spending.

A strict provider-enforced cash cap additionally needs a verified hard-denial mechanism or contract for an isolated allocation that includes concurrent usage, in-flight charges, delayed metering, taxes/fees and price/alias changes. Do not assume project/monthly budgets, alerts, prepaid balances or payment-card limits supply that guarantee. If the account has only soft controls, explicitly present the calculated bound and residual billing uncertainty; if the user requires an absolute cap, stop until a supported hard limit is verified. No pricing claim or limit setting is made by this local design.

## Cleanup and preservation receipt

Always journal cleanup in `finally`, including deployment/storage attempts whose acknowledgements were lost. Delete only exact owned names/objects, never a broad bucket empty or secret operation. Independently verify owned function absence and eventual guard-bucket absence, and unchanged baseline function source/version/configuration, secret names/digests and other storage metadata. Verify flags again using a still-valid non-dispatch attestation before expiry/deletion; absence of later evidence is an explicit proof gap. Keep local source, plan, binary/prefix and cleanup receipts private (0700 directories/0600 files).

There are **zero clinical RPCs, PostgREST patient requests, SQL patient queries or clinical writes** in the transport design. Attested/downloaded fixed code, a strict management/storage/OpenAI operation allowlist, and a retained operation journal provide preventive/no-attempt evidence. Optional existing metadata-only audit/statistics can corroborate no attributable DML without loading patient data. They cannot prove row-for-row equality: asynchronous counters, concurrent background writes and resets must be reported. A full live row-fingerprint comparison would itself read patient rows and is excluded; do not claim that stronger proof. If required for rollout acceptance, request a separately scoped preservation observer/authorization before running rather than quietly adding those reads. Unchanged migrations/schema/ACL metadata alone also does not prove unchanged row contents.

A run with unknown absence, changed baseline resources, lost raw evidence or unresolved preservation observations is **incomplete**, even if some model outputs parsed. Do not suppress such gaps or activate real processing.
