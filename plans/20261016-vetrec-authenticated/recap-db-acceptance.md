# Phase 2 database acceptance matrix

**Status: planned proof only. No recap database implementation, race test, restore test or hosted activation is established by this document.** The completed source-writer audit is a static review. Baseline `fd3f329a`; contracts: [recap-contract.md](recap-contract.md) and [phase-02-recapped-records.md](phase-02-recapped-records.md). Existing Phase 1 test results do not prove Phase 2 behavior.

## Proof environment and observation rules

Use one uniquely owned disposable PostgreSQL/Supabase runtime with synthetic patients, real local Auth/PostgREST and the actual recap RPCs. Disable scheduled delivery and use an owned fake provider. Record exact migration/source hashes, runtime identity, database version, assertion totals, zero real provider calls and removal of every owned resource. Never reuse or modify an unrelated development database. A separately authorized fixed-input OpenAI evaluation is additional evidence, not a substitute for these database checks.

For every concurrent scenario, use separate transactions/connections and an explicit barrier. Assign distinct `application_name` values to direct SQL sessions; record their backend PIDs. For HTTP RPCs, identify the actual waiting backend by the owned actor/job/attempt/action fixture and current query, with no source bodies in logs. Observe `pg_stat_activity.wait_event_type='Lock'`, the relevant `pg_locks` entry and `pg_blocking_pids(waiter_pid)` containing the expected blocker before releasing the barrier. A sleep or two successful sequential calls does not prove a lock race. Use bounded observation deadlines and fail if the expected wait was not observed.

Use the proposed private lock map in recap-contract.md: practice policy→optional actor quota→one action-family mutex→private job→private attempt→patient source mutex→private epoch row. Match its exact advisory key strings and record the observed PIDs/lock keys. Runtime tests must verify the implementation follows that design; final private table/trigger names and backend RPC argument prefixes remain implementation details to record with receipts.

## Epoch and source-writer races

The writer order found in the native code matters: problem operations acquire the patient `FOR UPDATE`; addendum insertion acquires its encounter `FOR UPDATE` through `aaa_release_lock_parent`; existing encounter save/sign acquire their encounter tuple. Writers reach the new epoch after the native mutation. Tests must use these actual RPC/trigger paths, not an invented writer that locks epoch first.

| ID | Planned ordering and observed barrier | Required result |
| --- | --- | --- |
| DB-L01 | Transaction A performs a real native problem edit and holds its transaction/epoch before commit. B starts recap preview/reservation and visibly waits on A's epoch. Commit A. | B captures the new problem version/content and current membership; reservation with the old preview fingerprint conflicts and leaves no partial job/manifest. This specifically detects a pre-wait or STABLE snapshot being reused. |
| DB-L02 | A holds the patient's epoch. B edits a native problem through the real writer and visibly waits at its AFTER epoch step while retaining native row/patient locks. A captures through the recap path and writes private recap evidence, then commits. | A reads the prior committed source and finishes without waiting on B's canonical row/FK locks; no deadlock. B commits afterward; a subsequent currentness read marks A's manifest stale. No clinical row is rewritten by recap. |
| DB-L03 | Repeat both orderings with `add_clinical_addendum` against a selected signed encounter; observe parent lock and epoch wait. | Writer-first includes the entire appended group. Reader-first captures the previous complete committed group and becomes stale afterward. No encounter row lock/FK is requested by recap. Encounter.version staying unchanged does not hide the append. |
| DB-L04 | Repeat both orderings with `sign_clinical_encounter` for a formerly unsigned row. | Signed-only discovery is fresh after writer-first commit. An explicitly selected unsigned source fails before capture. A newly signed unselected encounter never silently enters an existing selected subset. |
| DB-L05 | Repeat both orderings with patient identity edit, archival and deceased status change through `save_patient`. | Writer-first captures the new patient.version and lifecycle or conflicts with old expected identity. Reader-first can capture the prior committed historical context and is marked stale after commit. A fresh authorized historical snapshot remains possible for archived/deceased patients. No clinical-care or communication activation follows. |
| DB-L06 | A approves an outside-history extraction with action `link` for an existing eligible native problem, without changing its version/content; B captures and visibly waits. Reverse the ordering too. | Exclusion changes are serialized despite no problem UPDATE. Writer-first excludes the problem and counts the exclusion; reader-first is stale afterward when the selected optional group changes. A later local edit does not restore native eligibility. |
| DB-L07 | Use an extraction fixture whose independently stored pet_id differs from its actual problem's pet_id; exercise the trigger directly only in the owned test database. | The operation fails closed or bumps/serializes the actual affected patient's epoch. It cannot alter patient A's eligibility while locking only patient B's epoch. Normal approval RPC also rejects cross-patient linkage. |
| DB-L08 | Create a new native problem while recap captures the optional entire native problem group; test writer-first and reader-first. | No phantom is missed: either the row is included in a fresh capture or the saved manifest becomes stale after writer commit. Active/resolved and importance changes are also detected. |
| DB-L09 | Hold an actual private job/policy lock, start claim/dispatch/finish/review, then arrange a source mutation before releasing the lock. | The contract's proposed policy/actor/action/job/attempt/source/epoch order has no backwards acquisition or source-reader/native-writer inversion. Current sources are recomputed after all relevant waits, not just once before private admission. Dispatch/review results follow the final source state. |
| DB-L10 | Observe source change while a fake provider request is held after a successful one-shot dispatch. Release a syntactically valid cited response. | No automatic second provider call. The original manifest remains unchanged. A source-only change retains visibly stale output only if the exact policy remains current/approved and original job+attempt sessions remain valid after waits; acceptance is blocked. Changed/revoked policy/session yields sanitized outcome metadata only, without raw output/quotes or another provider call. |
| DB-L11 | Two concurrent recap reservations/previews for one patient, plus two readers for different patients. | Exact same-intent reservation is idempotent; no duplicate manifest/job. Different readers make progress without acquiring canonical source locks. Per-patient epochs do not become an undocumented global source lock. |
| DB-L12 | Catalog/call-graph review of future or maintenance batch paths; optionally a clearly separate synthetic multi-patient scenario. | Do not claim arbitrary SQL deadlock freedom. Current public source writers are scoped to one existing patient. A new multi-patient/multi-source transaction needs a separate ordering proof before release; passing single-patient reader/writer tests does not establish that proof. |

## Pinned design decisions and remaining proof

Exact transport projections, refusal enums/statuses, ancestry-first attempt ordering and reviewed/proposed claim shapes are pinned in recap-contract.md. The prior four design choices are now resolved in recap-contract.md: conservative finish retention, null outside-linked count when problems are unselected, ID-only owner policy recovery/cancellation with exact receipts, and the proposed deterministic lock map plus UTC/fixed-point budget computation. These are design commitments; they have not been implemented or proven by this document.

Implementation must record its concrete private relation/trigger names, demonstrate the advisory/row order with observed waits, verify fixed-point counter convergence at boundaries, and publish actual result/error receipts. The lock map deliberately serializes short recap transactions on a practice policy mutex; its latency and single-patient contention still need measurement. Never hold that mutex or a database transaction across a provider request. Arbitrary multi-patient maintenance SQL remains outside the established proof boundary.

No unresolved contract blocker is claimed here. Every matrix row still requires an actual receipt before it can be reported complete.
