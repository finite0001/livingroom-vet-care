# Native dispense corrections, returns and accounting — integration map

Status: read-only audit and proposed next scope. No correction/return implementation, provider commissioning or hosted change is claimed. This follows native fulfillment119 and selected release120; historical receipts and stock/billing entries remain immutable.

These independent screens presently cannot establish an immutable native dispense→return→stock/credit/refund chain.

## Actual gaps

There is no native correction/annotation ledger, physical-return disposition ledger, per-allocation returned-quantity accounting, return-linked stock movement, dispense/item-linked credit allocation, or refund attribution. Existing general adjustment/credit APIs do not close these gaps merely because a reason string names a dispense. There is also no native pickup amendment or selected-release disclosure of corrections. Preserve visible historical evidence instead of claiming an erroneous original never occurred.

`native_fulfillment_verified_dispense` verifies original artifact/allocation/movement/invoice-item relationships. It must continue verifying the original even after a correction, return or financial adjustment. Do not make mutable catalog state or later credit balance part of this historical verification.

## Invariants for the next exact contract

1. Separate clinical annotation, physical custody/stock disposition, accounting credit and cash refund. None implies the others. “Returned” must not silently mean resalable or refunded. Do not expose an unqualified “undo dispense” button.
2. Original dispense quantity, signed artifact, pickup, movements and invoice item stay unchanged. Corrections append actor/time/reason plus exact prior head and source references. An incorrect quantity is an attributed correction, not replacement of the original receipt.
3. **Never silently restore prescription allowance.** Native used/dispensed slot totals remain the historical debits. Clinical reauthorization, if needed, uses explicit DVM-reviewed cancellation/replacement or a separately designed authorization operation. A physical return or accounting credit cannot grant a refill.
4. Every physical return identifies actual original dispense allocations and quantities; cumulative returned amount cannot exceed the original amount per lot. Unknown origin/condition cannot be normalized to known lot or available stock. Review expired/inactive products and post-handoff custody explicitly. Quarantine/disposal is not a positive available-stock movement; current inventory lacks a quarantine ledger, so model this deliberately before enabling restock.
5. Stock disposition and its linked movement commit atomically under one idempotent receipt. Do not call public `adjust_inventory` with an independently replayable child UUID and then save a separate parent claim. Use a private materializer or one transaction with immutable bidirectional references and exact current-staff checks after waits.
6. Credits remain bounded by both the attributable original invoice item amount and the invoice's current uncredited balance. Preserve original cent rounding; partial quantity allocations need an explicit deterministic rounding/remainder policy. Existing unrelated invoice-wide credits must be reconciled rather than automatically attributed to a dispense.
7. An accounting credit is not a refund receipt. Link a native financial decision to the existing credit and, optionally, existing refund request/evidence separately. Never issue a second refund because a prior result is uncertain. No new provider account, credential, webhook or commissioning work is part of this phase.
8. Reviewed context must pin exact patient/household, authorization/dispense hash, correction and return heads, original allocations and already-returned quantities, and any stock/credit targets actually changed. Financial context includes invoice version/item set, credits and payment/refund reservation/reconciliation evidence; lock/hash dependencies must match the operation, not an unrelated aggregate.
9. Preserve request→optional refill→authorization→patient/client→invoice→product→sorted-lot ordering where those resources are needed. Existing adjustment is lot-only, credit/refund is invoice-only; avoid holding lot then acquiring invoice or invoking a public nested operation gate. Any combined operation needs observed contention with existing writers, not a blanket deadlock-free assertion.
10. Active staff can perform operational intake; clinician-attributed corrections and clinical conclusions require explicit DVM authority according to the agreed contract. Restock authority/condition acceptance must be an explicit reviewed practice policy, not inferred from active-staff membership. Print/release renders exact selected history and current correction status without leaking financial/provider internals.

## Ordered implementation proposal

1. **Contract and immutable annotation slice:** publish exact closed requests/receipts, correction targets/types, clinical versus operational authority, stale head guard, actor-scoped uncertain-write recovery and bounded history. Implement narrative correction and pickup amendment as explicit evidence; no stock, cash or allowance changes. Display original plus annotation in patient history/print. Design the versioned release disclosure in the same contract so an annotated record cannot continue appearing unqualified in newly sent packages.
2. **Physical return intake and disposition:** immutable per-dispense/per-lot quantity ledger, cumulative bounds and custody/condition/reviewer evidence. First make held/disposed outcomes honest. Only enable available-stock return when the explicit restock policy and atomic movement linkage are implemented and tested. No invoice credit or allowance effect.
3. **Financial association:** preview original item plus current invoice/payment evidence, create an explicitly attributed bounded credit, or link an existing credit without double attribution. Use existing refund subsystem for optional cash refund and preserve provider evidence/reconciliation; never bundle remote execution into the database transaction or describe request creation as refund completion.
4. **Final integrated history/releases:** expose corrections, returns, dispositions and financial references in staff history; keep client clinical disclosure appropriately scoped. Add fresh schema/version acceptance only where the frozen release representation changes. Old prints/releases/receipts stay recoverable and hash-verifiable.

Each slice must be usable and honest about unavailable follow-ups; these are ordered increments of the full correction workflow, not claims that narrative annotation alone completes returns/credits.

## Verification inventory and gates

Retain `supabase/tests/native_fulfillment.test.sql`, `native_fulfillment_concurrency.py`, inventory billing/product-locking tests, payment ledger/reconciliation/collection tests and native release tests. Reuse actual Auth/PostgREST runners in `tests/prescriptions/` and the owned native disposable harness; populated restore verification must include newly introduced immutable ledgers and exact links.

Required new checks: duplicate UUID exact retry versus changed request; actor revoked while blocked; two distinct returns against one original allocation; lot adjustment/receiving/catalog interaction; credit competing with unrelated credit/checkout/refund; ambiguous refund recovery; expired/unknown-condition return cannot enter available stock; zero and maximum quantities/cent rounding; original artifacts survive every action; no allowance restoration; selected-release invalidation/disclosure; correction/return history pagination and exact target isolation. Real provider refund acceptance remains whatever the existing commissioned payment workflow establishes, never inferred from synthetic local evidence.
