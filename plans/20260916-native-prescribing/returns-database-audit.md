# Native physical return custody/disposition — database audit

Status: bounded read-only design, not an implementation contract or migration. Parent has now selected the strict restock boundary recorded below; exact RPC contract is forthcoming. Baseline includes fulfillment119, release120 and corrections121. No provider, money, prescription allowance or hosted changes are proposed here.

## Exact existing dependencies

- `native_dispenses` binds immutable authorization/patient/slot, invoice/item, actor/time and quantity. `native_dispense_allocations` has `{id,dispense_id,lot_id,movement_id,quantity}`, unique `(dispense_id,lot_id)` and unique movement ID. Quantity is positive `numeric(14,3)`; allocation IDs are stable internal source identities.
- `native_fulfillment_verified_dispense(uuid)` in `20260916072509_native_fulfillment.sql` verifies allocations against frozen document, original negative `inventory_movements` quantities/kind/actor, immutable invoice item and full artifact hash. Reuse it before accepting an attributed return; never weaken this historical verification after restock.
- `inventory_lots` metadata/product/expiry/location is immutable. `inventory_movements` quantity is signed nonzero `numeric(14,3)`; kinds currently receive/adjust/dispense. All movement sums represent **available stock**, so held/quarantined/disposed custody cannot be inserted as positive movement.
- `adjust_inventory` in inventory billing serializes request UUID, locks lot UPDATE, enforces nonnegative balance, and supports positive adjustments. Effective118 patch rechecks active staff after request wait. It does not lock product or verify any native return/policy. Receiving and treatment/dispense use product SHARE before lot UPDATE. See `20260916070108_inventory_product_before_lot_locking.sql`.
- Native dispensing serializes optional refill gate before authorization gate, then patient/client, invoice, product and sorted lots. Correction append and pickup both share authorization gate. Return operations can use authorization gate without acquiring refill or invoice locks; stock disposition adds product SHARE then sorted original lots UPDATE.
- `native_rx_usage_context` counts original slot debits, opened slots, forfeiture and unopened allowance. Returns must not change this function's meaning, original allocations, slots or fulfillment head. A returned dose remains originally dispensed; replacement signing reviews an explicit return summary separately if later requested, never converts returns to recovered allowance.
- `native_pickups` has one immutable row per dispense. Correction121 preserves original handoff and a separately attributed amended interpretation (`recorded_in_error`/`corrected_handoff`). None establishes the item's actual current custody, condition or lot identity.
- Schema11 release and printV2 include correction summaries/history but no return evidence. Relevant functions: `native_correction_summary`, `native_correction_disclosure`, `read_native_prescription_print_v2`, `release_preview_v11_internal`, `invalidate_native_correction_release`, and the schema10 compatibility wrapper. Existing release source registry selects native authorization/dispense IDs.

## Proposed ledger shape, pending root contract

Use separate immutable custody ledgers and operation receipts; do not overload annotation, pickup or terminal authorization events.

- `native_return_intakes`: exact verified dispense/patient/authorization hash, actor/time, stated source/custodian, custody received time, condition statement, reason, review context/hash and immutable document.
- `native_return_lines`: immutable intake line ID, exact original source allocation ID, quantity in the original signed stock unit, asserted lot identity/condition. Index by dispense+allocation; no automatic conversion between tablets, containers, doses or volume.
- `native_return_dispositions`: append-only event ID, intake line, quantity, `disposed` or `restocked`, actor/time, reason, exact prior custody head/hash, policy snapshot/hash when restocked, and immutable document. Partial dispositions are explicit; held balance equals intake minus all dispositions. Never edit an intake into a disposed/restocked row.
- `native_return_stock_links`: immutable unique disposition→positive movement mapping for restock only; original allocation/lot/product and actor/quantity must agree. Dispose produces no stock movement. Disposition+movement+receipt commit atomically.
- `native_return_events` or an equivalent per-dispense sequence/head: ordered intake/disposition change tokens with verified canonical chain; independent of original native fulfillment/correction heads. Same authorization gate serializes competing intakes/dispositions.
- `native_return_operations`: exact actor+UUID+kind+closed request receipt and canonical hash, same-actor current-staff recovery. Frozen requested quantities stay exact strings; returned/projection quantities fixed-three; initial and derived totals use bigint milliunits/unbounded SQL numeric sums, not floating point.
- Versioned `native_return_restock_policy` plus immutable policy revision history. Default absent/disabled means restock denied, while held intake and disposal remain usable. ADMIN configures a separately documented clinical approval/reference and permitted review workflow; enabling a Boolean alone must not imply clinical suitability. Active DVM is required for restock; root contract will define exact policy commissioning/reviewer fields before SQL.

Suggested RPC surface: `preview_native_return_intake(target,lines,custody facts)`, `record_native_return_intake(id,request)`, `preview_native_return_disposition(target,intake lines,quantities,disposition)`, `record_native_return_disposition(id,request)`, `recover_native_return_operation(id)`, target-bound current summary and bounded sequence-cursor history. Names and exact JSON remain for the implementation contract. All writes include explicit attestations, expected heads/context hashes and separate action types; no hidden movement or financial side effect.

## Quantity and unknown-lot decision

Known-attribution intake must satisfy both total returned-for-dispense <= original dispense quantity and cumulative returned-for-allocation <= its original quantity. Count **all** previously accepted intake quantities, including held, disposed and restocked; disposition never frees the return cap. Otherwise the same issued quantity could repeatedly re-enter stock. A later independently dispensed event has its own allocation/cap.

Parent selected original allocation attribution for this increment. Do not guess allocation from only drug name or latest lot. Unknown custody/condition on an otherwise identified original allocation may be held/disposed, but cannot restock. Items whose original allocation cannot be established need an explicitly unresolved custody workflow outside verified native attribution; this contract must not claim that known-lot native intake already covers them.

Physical receipts exceeding documented original quantity cannot be silently clipped or fabricated into valid allocations. Either refuse native attribution with a clear unresolved-custody workflow, or design a separately labeled non-attributed intake; do not alter original dispense to make the count fit.

## Locks, policy and reviewed evidence

1. Stable operation UUID gate; exact stored request replay after current active-staff check.
2. Existing authorization advisory gate. Recompute immutable dispense/allocations, current return head, cumulative returned quantities, held remainder, correction/pickup evidence and patient target. Archived/terminal authorizations remain valid historical return targets.
3. For restock only, require current active DVM and lock/read exact enabled policy revision before product/lot locks; policy updates must never wait for authorization/stock locks. Recheck reviewer authority and effective approval after waits. Fixed lock order must cover the final configuration writer too.
4. Product SHARE then sorted original-lot UPDATE. Recheck product/lot identity, current expiry on America/Denver clinical day, active status and unit compatibility, policy constraints and reviewed quantity. Parent requires clinic_retained custody, sealed/intact condition, documented controlled storage, and **no original pickup row at all**, even if later amended as recorded_in_error. Other custody/unknown condition is held/disposed only. Do not change original lot metadata or use receiving to create a guessed replacement lot.
5. Append disposition, linked positive movement with dedicated `native_return` (or contract-selected `return`) kind and immutable receipt in one transaction; verify postwait actor/policy. Add the new movement kind through an additive constraint change and verify positive quantity plus exact return↔movement links; never allow a linked native return to be mistaken for a generic adjustment. Generic positive adjustment remains an independent legacy capability; a new native policy gate does **not** establish that all manual stock adjustments are policy-governed. Avoid claiming global prevention unless general adjustment workflows are explicitly brought into scope.

Held intake/disposal does not need product availability or unexpired stock; those conditions must not prevent recording already-returned expired/damaged goods. Current custody is explicitly observed/attested at intake, not inferred from original pickup or an amendment. Bind original pickup and latest correction head to reviewed context so changes during review force re-review, but do not prohibit honest intake simply because historical pickup is missing/disputed. Record that uncertainty.

Never call public adjust_inventory using a separately recoverable child UUID and then record the parent return afterward. Use one private materializer/transaction with immutable links; a caller must not be able to replay a movement independently of the reviewed disposition. Preserve nonnegative and finite numeric bounds, and avoid lot→product/invoice lock inversion.

## Release/print and correction interaction

A return does not rewrite pickup or retract an annotation. A later pickup amendment does not undo received custody or disposition. Staff history presents original dispensing, original/amended handoff, then separately observed return custody and disposition. “Disposed” means an attributed completed disposition, not merely a proposed future action; reasons/review must match the label.

Because schema11 cannot disclose returns, plan explicit next print/release version with authorization-level return summary and bounded selected-dispense return history. Keep original allowance separate from returned/held/disposed/restocked totals. Before enabling returns, choose one honest gate: new disclosure implemented, or affected legacy print/release generation fails closed. Saved releases/receipts remain immutable and historically readable.

New intake/disposition events must invalidate relevant schema10/11/new-version releases selecting the same authorization or a dispense whose embedded authorization summary changes. Fresh schema10 compatibility must remain closed for corrections and additionally returns; schema11 must not silently omit newly relevant return facts. Private worker composition retains service-role/stored-actor behavior, exact inherited original-byte binding and explicit policy acceptance for any new schema. Sorting authorization locks, append-only invalidation and compatible release FK KEY SHARE remain required.
