# Reviewed record email delivery

Schema5 source-backed originals now require actual downloaded bytes to match the frozen lab/external capture SHA256 in both the shared builder and SQL capture RPC. Exact already-captured preparation recovers its immutable receipt without downloading current files; this does not override final delivery eligibility. The same checks cover document-link materialization. See [source byte binding](release-source-byte-binding.md).

This increment connects a confirmed EMAIL release to the durable Resend HTTP outbox. Preparation does not send. A staff member reviews the actual generated HTML report, downloaded frozen originals, message, recipient and manifest before explicitly queueing. No SMS record links, public Storage URLs, raw-document-ID attachment API, or PDF conversion is introduced. An HTML report is attached as `medical-records-<release-id>.html` with `text/html`, never disguised as a PDF.

## Durable staff workflow

1. `prepare_release_email(p_request_id, p_release_id, p_conversation_id, p_subject, p_body, p_release_hash)` stamps the authenticated staff actor and persists exact intent. The release must be current, match the conversation household and its current email, and pass clinical-form acceptance and suppression checks. Only one unresolved request exists per actor/release. An unchanged UUID is idempotent; changed intent cannot reuse it.
2. The authenticated `prepare-release-email` Edge Function accepts those same six arguments. Its gateway retains `verify_jwt=true`; the handler also verifies the bearer with `auth.getUser`, then uses the staff JWT for preparation. A restricted service context rechecks actor, household, release hash/eligibility and clinical policy before reading originals. Only the selected private `patient-documents` objects are downloaded. Size and PDF/JPEG/PNG signatures are checked; a deterministic escaped report is generated from the immutable release snapshot. The full serialized provider request, including canonical sender/reply-to, recipient, subject, body and ordered Base64 attachments, is frozen exactly once.
3. `recover_release_email(p_release_id, p_request_id optional)` returns the latest own non-abandoned request, including a queued receipt after a lost enqueue response. Its shape is `{request, payload_hash, manifest, report_html, purged_at, receipt}`. Request states are `preparing`, `ready`, `queued`, and `abandoned`. Manifest entries contain filename, MIME, byte size, SHA-256 and selected document ID (null for the report). Original Base64 bytes and private paths are not included in ordinary recovery.
4. `read_release_email_attachment(p_request_id, p_index)` lets the original active staff actor download one exact frozen attachment for review. It returns `{filename, content_type, content}` with Base64 content. This is a request-scoped authorized download, not a public link or arbitrary document-ID lookup.
5. `enqueue_release_email(p_request_id, p_reviewed_payload_hash, p_attest)` checks the exact reviewed manifest/payload, reauthorizes the release and household, and atomically creates an outbox row plus immutable release link. Existing regular message preparation and enqueue APIs still reject raw `attachment_ids`. The new release path has its own durable preparation and review contract. Identical queue retries return the existing receipt.
6. `abandon_release_email(p_request_id)` only abandons the actor's own unqueued request. Queued history is not erased. “Compose a separate new email” is an explicit action after a recorded queue receipt; ordinary reload never implies a new send.

`ReleaseEmailComposer` is mounted inside the opened patient release. It can create/use the household's active conversation through the existing `ensure_active_conversation` RPC when the household has none. Recovered conversation, subject, message and manifest stay fixed. Local validation runs before reserving a UUID. Definitive server rejection with confirmed absence of a row permits editing; ambiguous outcomes preserve the request and require recovery. Cached older receipts cannot overwrite a newly prepared request. The composer contributes to the existing shared dirty guard, including blocking another package's confirmation from remounting it.

## Dispatch and retry

The dispatcher reads a frozen payload only for its current, unexpired, not-yet-started outbox lease. It verifies the complete serialized UTF-8 payload hash and exact sender, reply-to, recipient, subject and body. It sends that same stored string; it does not rebuild attachment content on retry.

Immediately before the provider request, the new `start_communication_attempt` wrapper calls the same private release eligibility implementation used by staff reads. It rechecks active actor, current household contact, suppression, clinical policy, all selected source versions/history, and stored original availability. The existing reminder guard and ordinary sender/actor/recipient/idempotency checks remain in the call chain. Private release cores are revoked from public, anonymous, authenticated and service-role callers; only narrowly authorized wrappers can invoke them. `clinical_require_staff`, clinical table policies and grants are unchanged.

The existing outbox ID remains the Resend idempotency key. Sender changes, payload corruption, invalidated releases, stale contacts or retired clinical policy prevent a provider attempt. Ambiguous provider outcomes preserve the existing reconciliation workflow and its 23-hour safety cutoff. Queueing and provider acceptance are displayed separately from delivery.

## Limits and provider evidence

Resend documents a maximum email size of 40 MB including Base64-encoded attachments, and disallows attachments on its batch endpoint. This implementation uses the single-email HTTP endpoint, accepts at most 24 originals plus one report, and caps the **entire serialized UTF-8 JSON provider request at 32 MiB**, including message text, headers represented in the payload, filenames and sender metadata. It checks estimated size before fetching originals and exact size after serialization. Oversized requests require a separately reviewed smaller release; no file is silently omitted. [Resend attachment documentation](https://resend.com/docs/dashboard/emails/attachments), [send-email API](https://resend.com/docs/api-reference/emails/send-email).

Resend retains idempotency keys for 24 hours and rejects reuse with changed content. The existing 23-hour application cutoff is intentionally preserved; expired uncertainty requires evidence-based reconciliation. [Resend idempotency documentation](https://resend.com/docs/dashboard/emails/idempotency-keys).

## Private bytes and retention

The request, payload and link tables have RLS and no direct anonymous, staff or service-role DML/read grants. Narrow RPCs expose only authorized intent/manifest/report or one owner-reviewed attachment; lease-bound service reads expose the frozen provider payload. Errors never return Base64, private paths, provider payloads or SQL diagnostic context. Audit entries retain hashes/manifests and review/queue evidence, not report or attachment bytes.

`purge_expired_release_email_payloads(p_limit default 100)` is service-only. It removes payload bytes after 90 days for abandoned requests or provider-accepted/delivered messages with a receipt, while retaining the immutable manifest/hash and queue/review audit. It never purges pending or uncertain delivery payloads. A production daily operator/scheduled call is still required; no cron is silently installed. Failed/uncertain requests require operational resolution before their retained bytes can be expired safely. They must not be blindly resent or silently deleted to meet a timer. Clinical record snapshots and their original source documents follow the practice's separate medical-record retention policy.

No live send, provider configuration activation, cloud migration or private production-byte download was performed during implementation. Validation uses local rollback SQL fixtures, mocked providers/private downloads, and browser request interception. Deployment still needs a staff-authenticated staging check of the Edge gateway and configured practice sender/reply mailbox. This release form continues to require Dr. Edler's recorded acceptance.

## Shared renderer and validation

The report, chart-history, clinical-history and vaccine-certificate renderers live in `supabase/functions/_shared` so deployed Edge bundles do not depend on files outside the function tree. Existing browser import paths re-export the same functions and types. This is one implementation, preserving deterministic output and existing fixture/public-import compatibility. PR37 at `109b891` added CI verification for all 14 Edge entry points with frozen Deno dependencies. This replaces the earlier lockfile integration caveat; module checks still do not establish a successful hosted gateway/provider round-trip.

Validation includes 42 new SQL assertions; prior release (97), outbox (44), recovery (26), and reminder (49) assertions; adapter/provider/recovery unit tests; and browser recovery after lost capture and queue responses, fresh-household conversation creation, local validation, malformed-response isolation, and protecting an active composer from another package's confirmation. All provider calls are mocked.
