# Reviewed historical medical-record originals

Migration `20260913420000_external_record_provenance.sql` implements the database foundation for preserving a manually obtained ezyVet medical-record export. Living Room Vet is primary; ezyVet is an import source. This is a local, reviewed manual-file workflow. It neither validates an ezyVet API response contract nor authenticates the exporting clinician or provider. No provider calls, source credentials, automatic chart conversion or sending are enabled by this migration.

Existing private documents already preserve uploaded PDFs/images. This increment adds immutable association with an approved ezyVet animal mapping, verified local file bytes, original/replacement history, durable review recovery and a separate veterinarian acknowledgment. It does not create SOAP, problems, treatments, due dates, signatures, stock movements, invoices or payments. Native clinical records and their author identity remain unchanged.

## Source and authority

An active administrator selects an existing `ezyvet_record_links` row with `resource='animal'`, scoped to the patient using the existing administrator RLS read policy. No mapping UUID needs manual entry. The server derives local patient/household and source origin, site and external animal ID from that immutable approved mapping. Trial and production sites remain distinct.

The administrator supplies a human-readable export reference, receipt date and review reason and selects a ready same-patient `medical_record` document at its exact version. The export reference is a staff-reviewed reference, not an assumed vendor field. Series identity is mapping plus exact export reference; separate exports can use separate references. A replacement retains that identity, requires a new document and names the current prior record. An already-preserved document cannot be approved under another series. Earlier files and acknowledgments remain immutable.

A service downloads the actual ready private object and computes SHA256; the staff does not enter a hash. The digest proves the bytes inspected, not vendor origin, patient identity, completeness or clinical correctness. The administrator explicitly approves the exact staged provenance and verified bytes. A separate active DVM may acknowledge that exact record; the role is the existing clinical `DVM` role. Import never creates an acknowledgment, and an acknowledgment never covers later replacements automatically.

## Durable contracts

All UUIDs are caller-retained opaque operation IDs. Staging and approval mutations require the original active administrator. Exact retries return existing results before present-day patient/document eligibility checks; changed arguments fail. This preserves acknowledgment of a committed transaction after a later document void or patient edit. Fresh approvals still require current patient and document versions. Mapping-row locks serialize series changes; patient/document share locks serialize approval against edits and voids.

- `stage_external_record_receipt(p_id,p_animal_link_id,p_expected_pet_version,p_document_id,p_document_version,p_export_reference,p_received_at,p_previous_record_id,p_review_reason)` returns an immutable receipt. It freezes source identity, patient version, document MIME/size/version, prior head and review reason under `receipt_hash`; entry method is `staff_reviewed_manual_export_v1`.
- Service-only `external_record_capture_context(p_receipt_id,p_actor_id)` returns `{receipt,document:{id,version,bucket,file_path,mime_type,file_size},capture|null}`. It requires the original active administrator and original ready document.
- Service-only `capture_external_record_bytes(p_receipt_id,p_actor_id,p_expected_receipt_hash,p_document_version,p_content_sha256,p_file_size,p_mime_type)` returns immutable `{receipt_id,actor_id,receipt_hash,document_version,content_sha256,file_size,mime_type,capture_hash,captured_at}`. Repeated capture must match exactly. Browser callers cannot execute it.
- `approve_external_record_import(p_id,p_receipt_id,p_expected_receipt_hash,p_expected_capture_hash,p_attest)` returns the immutable version. Original or replacement kind is server-derived; its reason and prior record come from the staged receipt, not fresh caller values. Approval cannot reinterpret the manual export as native chart entries.
- `recover_external_record_receipt(p_receipt_id)` returns `{receipt,capture|null,record|null}` for its original administrator, or null when no owned receipt exists. It reads historical receipts after voids and supersession.
- `list_external_record_receipts(p_pet_id,p_before_at=null,p_before_id=null,p_limit=50)` returns `{pet_id,receipts:[recovery envelopes],has_more}`. It includes the actor's prepared and approved receipts, so clearing a browser pointer does not lose server-side discovery. Keyset pagination uses receipt `created_at,id`, descending; both cursor values are required together. Limit is 1–100.
- `read_external_record_history` has the same cursor signature and returns `{pet_id,records,has_more}` to active clinical staff. Each record includes its immutable version row, `provider='ezyVet'`, entry method, source origin/site/animal identity, received date, capture, current document status and exact-record acknowledgments. Source identity is nonsecret and distinguishes equal animal IDs across sites; no raw staging payload, credentials, Storage path or usable URL is returned.
- `acknowledge_external_record(p_id,p_record_id,p_pet_id,p_expected_capture_hash,p_expected_document_version,p_attest)` requires active DVM access and a ready exact document. It creates only an acknowledgment attributed to that reviewer, not a source clinician's signature.
- `recover_external_record_acknowledgment(p_id)` returns the active DVM's own exact acknowledgment or null, including after a subsequent document void. This is read-only recovery independent of the current history page.

New tables have RLS enabled and no direct API-role reads or writes. Receipts, byte captures, record versions and acknowledgments reject updates/deletes even through ordinary privileged SQL. Only narrow security-definer RPCs are exposed. No usable document URLs persist in these ledgers.

## Validation and remaining gates

The SQL fixture uses explicitly synthetic mapping/document metadata and digest values; it is not actual Storage or ezyVet acceptance. Tests exercise role/actor isolation, missing proof, changed retry fields, exact recovery, same-patient/version guards, replacement provenance, independent DVM review, bounded pointer-free discovery, immutable history, and unchanged native patient/chart/treatment/stock/payment state. The concurrency fixture observes actual PostgreSQL lock waiting for competing originals/replacements, patient edit versus approval, and both document void/approval orders. It creates and cleans only owned random local fixtures and makes no provider requests.

Run the additive migration on a migrated local stack, then the SQL fixture and `python3 supabase/tests/external_record_provenance_concurrency.py`. CI can pass `--project-config supabase/config.toml` to select its own container. No database reset is required or permitted against a shared working stack.

The companion Edge verifier and staff UI are separate increments. Actual hosted staff/Storage workflows and Dr. Susan Edler's review remain commissioning requirements. Real ezyVet authorization, API entitlement/read scopes, source endpoint/sample contracts, attachment/export completeness, legal use confirmation documented in the existing import plan, supervised migration reconciliation and clinical mapping acceptance remain external gates. Manually preserving an original does not prove a complete patient migration.

Structured historical diagnoses/reactions, SOAP conversion, vaccine administrations/due dates, prescriptions, source attachments via API and automatic backfill remain unimplemented. They require separate explicit mappings and acceptance; no generic JSON field is treated as a diagnosis, signature or vaccine claim here. Existing weight import remains independent. This increment does not automatically include external-record provenance in an existing frozen medical release; any such renderer/projection extension needs separate reviewed schema acceptance.
