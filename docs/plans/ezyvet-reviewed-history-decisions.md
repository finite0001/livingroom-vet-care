# Reviewed API history — implementation decisions

Phase2 of [the clinical migration plan](../../plans/20260913-ezyvet-clinical-import/phase-02-reviewed-chart-history.md), based on PR106 (`e80cf62`). These are implementation decisions, not Dr. Edler's clinical acceptance. Migrations5000/5100 are reserved for reviewed history and schema6 releases, subject to final inventory review.

- Preserve imported narrative, raw date/category/chain/author/status and exact source observation separately from administrator approval and a local DVM's clinical decision. Do not sign imported prose through the native SOAP endpoint.
- Optional unresolved consultation context must be explicit. A known same-site consultation/patient contradiction must reject approval rather than be concealed as unresolved. Do not invent meanings for zero, empty or unknown source references.
- Initial inactive/unknown source status may be reviewed without treating it as a resolved clinical condition. DVM extraction requires explicit local status and importance; it does not infer a diagnosis or reaction from prose.
- Native problem constraints are title1–250 characters, notes up to10000, nullable canonical ISO onset date, status `active|resolved`, importance `routine|high`. Align the existing editor's oversized title limit as part of integration.
- Create and link are different actions. Create calls the existing clinical validator atomically with immutable provenance. Link verifies the existing target/version and leaves all native fields unchanged. Several distinct problems may legitimately reference one source history; operation/item identity supplies idempotency, not one-history-to-one-problem uniqueness. Within a single extraction, select only one approved version of each source identity so later discrepancy review can resolve every original source unambiguously.
- Preparation, approval, abandonment and pointer-free discovery use actor/patient/kind-bound identities. An identity-only tombstone can block delayed preparation after abandonment; it cannot overwrite another actor's operation. Exact committed recovery precedes mutable-source eligibility checks but still requires the appropriate active actor/role. Attestation/null checks fail closed.
- A DVM discrepancy review sees newly administrator-approved current history versions through a safe clinical projection, never raw staging. It pins the exact reviewed versions/heads for the complete original source set and changes no native fields. Changed-from-original and unresolved-current-attention are separate facts; the next source revision creates attention again.
- Fix the actual native problem tuple/patient lock ordering before adding extraction. Keep patient/source-head/target/request ordering consistent with ingestion, release previews and treatment alert review; prove contention with observed waiters and both commit orders.
- Schema6 retains schema5 lab/external byte verification in both SQL and JavaScript. All schema1–5 frozen artifacts remain immutable. Text-only imported histories do not acquire document-byte verification claims.
- Selected native problems automatically include all extraction provenance. Full imported narratives remain explicitly selected through `imported_history_ids`; compact source references disclose whether the full narrative was included. Private administrative reasons and unrelated staging keys do not enter recipient output. A history-only package must work without implicitly selecting patient summaries or other clinical records.
- Historical approved histories remain selectable with accurate current/source-discrepancy labels, provided identity remains valid. Later source/provenance changes invalidate existing delivery eligibility and require fresh review; they do not erase historical records. Schema6 clinical-policy acceptance remains disabled.

Actual source access/sample validation, Dr. Susan Edler's acceptance, hosted staff operation and provider delivery remain commissioning gates. Vaccinations, prescription history, source attachments and full migration reconciliation remain required later phases; this increment does not redefine complete migration around history/problems alone.
