# Reviewed weight provenance in record releases

Release form v4 includes the provenance associated with every selected dated weight. The explicit `preview_record_release_v4` staff API returns v4 when weights are selected; without weights it retains the existing applicable v1–v3 snapshot. The practice operator must record clinical acceptance with `accepted_schema_version = 4` before confirming v4. Migration2500 does not seed acceptance. Dr Susan Edler must review the exported wording, disclosure of review reasons and workflow before operational use.

Each selected weight retains its immutable native measurement and local recording identity/date. `import_provenance` contains **all** associated reviewed ezyVet approvals, ordered by approval time/ID, including create versus link, original source value/unit/timestamp, reviewed local values, reviewer UUID/time/reason, and all dated source reviews. Source reviews include their observed source version and values. Reviewer IDs identify local reviewers; no source clinician is fabricated. A review of changed source data does not automatically correct the local measurement. An unreviewed latest external source version is explicitly labeled. No raw staging payload, API origin, credentials or integration configuration is exported. Review reasons are included as authored and HTML-escaped, without automatic clinical redaction.

`latest_source_version` and `latest_source_reviewed` describe the observed state at package confirmation. New approval associations, source-review appends and external source-head updates invalidate affected v4 packages without changing their frozen content. Preview, confirmation, capture and final provider preflight retain shared native-weight locks; ledger/head mutations acquire exclusive locks on those same rows. Hash comparison rejects changes between review and confirmation. The existing exact capture/queue/recovery and private service wrappers remain in force. An already-confirmed retry returns its original immutable receipt; eligibility must be read separately.

The old preview API keeps its v1–v3 shape. It cannot create a new package of imported weights without the v4 review. Existing confirmed v1–v3 packages keep their snapshot, exact renderer output and historical eligibility behavior; later provenance activity is not retroactively attached to them. Version3 recomputation explicitly uses the preserved private version3 preview. Updating the accepted form does not rewrite prior artifacts. Private preview/read functions remain denied to staff and service callers; only the existing scoped entry points and new staff v4 preview are granted.

The output remains a deterministic printable HTML report and a truthfully named `.html` email attachment. No PDF generation, SMS link, provider send or deployment is part of this change. The 1MiB snapshot bound requires splitting large packages rather than silently truncating source histories.

Validation covers all approval associations, changed source values, source-review reasons, original/local distinction, cross-patient denial, v4 acceptance, old-UI rejection, immutable old and new packages, stale hashes, legacy eligibility, private grants, source-head invalidation, and changed-provenance denial at email capture/final provider preflight. Renderer tests preserve exact v1–v3 fixture hashes from parent109b891 and verify escaped v4 report/email content. Browser fixtures use the v4 API and separate v4 policy gate.
