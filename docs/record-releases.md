# Selected medical-record release packages

This module creates an actual review artifact and immutable confirmed package. It does not send records, generate a PDF, fetch original file bytes, or enable attachments on the existing communication outbox. Confirmation remains disabled until a trusted operator records Dr. Edler's acceptance of the release form and workflow in `record_release_policy`. The table starts empty, is not writable by staff or service-role callers, and has an audit trigger. Preview remains available for clinical review before activation.

## Dependencies and stacking

Release commits are stacked onto the clinical/inbox/lab/anesthesia/care-reminder foundation. The earlier duplicate certificate backend cherry-pick was removed during rebase; no certificate schema or UI commit is replayed by this branch. Certificate content is delegated to the shared frozen-certificate renderer, including future supported certificate snapshot versions. No enqueue/recovery function or raw `attachment_ids` contract is changed.

## Explicit content boundary

`p_selection` contains optional arrays `encounter_ids`, `certificate_ids`, `lab_order_ids`, `document_ids`, `dental_ids`, `qol_ids`, `anesthesia_ids`, `lesion_ids`, `problem_ids`, `weight_ids`, `treatment_ids`, and `patient_summary_ids`. Omitted arrays are empty: no records are included by default. Each array allows up to 100 unique UUIDs. “Some” means selected IDs; “all” means all explicitly reviewed eligible IDs within that bound, split into additional packages if necessary. There is no silent catch-all selection that grows after review.

- A selected SOAP encounter must be signed and belong to the patient. Its S/O/A/P text and **all** signed-record addenda are included. Individual addenda cannot be omitted to hide a later correction. Draft encounters and visit-location workflow fields are excluded from the SOAP source. Select structured problem/diagnosis history separately to include its authored clinical notes.
- Selected certificates must belong to the patient and have no invalidation events. The exact issued snapshot, issuer signature/attestation, and issuance time are retained. Current patient/catalog values never rewrite the embedded certificate.
- A selected lab must be in resulted status and have its original report explicitly selected in `document_ids`. Only test name, accession, collection/result dates, order version and report reference are included. Lab notes, ordering/planning instructions, interval/template settings, and override reasons are excluded. Lab order versions are frozen; a changed result requires a fresh package.
- Every original must be `ready`, `client_shareable`, and owned by the same patient. Private/internal, uploading, voided, abandoned, other-patient, and missing Storage objects are rejected. Name, version, MIME, byte size, document date and immutable private object reference are frozen. The package contains no signed URL. The patient panel can separately request a short-lived, same-origin private original download for staff review after rechecking patient/ready/shareable status.

All contents must still be reviewed for disclosure: signed SOAP text may itself contain sensitive information. This module does not automatically redact the original. Exclude an unsuitable encounter or use a separately approved redaction workflow; do not claim the software can recognize private prose automatically.

## RPC contract

`preview_record_release(p_pet_id uuid, p_client_id uuid, p_channel text, p_recipient text, p_selection jsonb)` returns `{snapshot, source_hash}`. It requires active staff. The patient must belong to the specified household, and the normalized EMAIL/SMS recipient must match that household's current primary email/phone. Wrong-household recipients cannot be substituted. Snapshots freeze patient/household identity versions, selected structured content, all selected source versions, and original metadata. The SHA-256 covers PostgreSQL's canonical JSONB snapshot serialization; it is **not a hash of attachment bytes or rendered HTML**.

`confirm_record_release(p_id uuid, p_pet_id uuid, p_client_id uuid, p_channel text, p_recipient text, p_selection jsonb, p_reviewed_snapshot jsonb, p_reviewed_hash text, p_attest_review boolean)` requires enabled clinical acceptance and explicit review of both contents and recipient. Pass the complete preview and its hash unchanged. The server recomputes both under source locks and rejects stale/altered contents with `40001`. Keep the UUID and original payload through ambiguous responses. Identical retries by the original actor return the same row, including after later invalidation; the caller must read current eligibility before exporting for delivery. Changed payload or another actor cannot reuse the ID.

`read_record_release(p_id uuid)` returns `{release, events, eligible, ineligibility_reason}`. The release omits its internal retry request and always retains the original immutable snapshot. This read verifies current source eligibility/hash when no event already disqualifies it. Storage absence or recipient changes fail closed. Source eligibility is **not proof of messaging consent or successful delivery**.

`withdraw_record_release(p_id uuid, p_release_id uuid, p_reason text)` appends a reasoned, actor-stamped event. The event UUID and exact payload are idempotent. No history update/delete is available.

`authorize_record_release(p_id uuid, p_client_id uuid, p_channel text, p_recipient text)` requires active staff, enabled clinical acceptance, current package eligibility, and the exact household/recipient association. It returns the authorized package bundle; it accepts **no raw document IDs**. No transport worker is granted execution. A future server-side outbox adapter must recheck consent/suppression, actual recipient, current package eligibility, immutable original references, provider size/MIME limits and delivery state at send time. A package must not become a bypass for existing messaging preparation or recipient controls. Keep the current raw-attachment rejection intact until that adapter is reviewed and tested.

## Extended chart sources and format compatibility

`dental_ids`, `qol_ids`, and `anesthesia_ids` require signed records from the same patient and include every addendum. Dental exports preserve per-tooth findings/procedures/manual measurements. QOL exports remain qualitative and retain the reviewed template version; no score or prognosis is generated. Anesthesia exports preserve documentary observations/events and recovery notes. Draft revisions and transcription-workflow descriptions are excluded.

`lesion_ids` selects a complete stable body-map history: all dated observations, normalized coordinates, measurements, and every correction. Corrected observations remain visibly labeled historical measurements. The schematic is species-neutral and not an anatomical diagnosis. These are explicitly selected staff observations, not a fabricated signed diagnostic chart. Photo/original-document links are included only when their document IDs were separately selected and passed the normal shareability checks; private/unselected photo IDs do not leak into the snapshot.

Packages selecting diagnosis, allergy/profile, weight, or treatment history use snapshot version 3. Selections using only the earlier eight families continue to produce v2. Existing v1/v2 packages validate against their original private compatibility helper and are not rewritten or invalidated by this expansion. The operator policy `accepted_schema_version` must cover the exact reviewed format; the updated patient panel requires version 3 acceptance. Approval of an earlier form alone does not activate the new history form. Dr. Edler should review complete samples before operator activation.

## Invalidation and concurrency

New SOAP/dental/QOL/anesthesia addenda, new lesion observations or corrections, certificate invalidation events, lab-order revisions, document changes/voids, diagnosis revisions, treatment corrections, or patient/household changes append `source_changed` events to existing packages. Original package contents never change. These conservative invalidations may require rereview even when a source edit affected a field excluded from print, because the reviewed version changed.

Encounter/addendum and certificate/event parent locks coordinate confirmation with concurrent corrections. Lab locks precede document locks, matching the lab writer's lock order. Read/withdraw locks coordinate package eligibility. Original Storage metadata is rechecked during authorization; ordinary staff cannot replace finalized originals. A privileged operator changing Storage outside the application is not covered by a cryptographic hash of the original bytes. A transport adapter should verify any additional binary integrity evidence it needs before attaching bytes.

Already downloaded or delivered copies cannot be remotely recalled. Withdrawn/changed copies remain available as visibly invalidated historical artifacts; only a new reviewed package can restore delivery eligibility.

## Review/export component

`renderRecordRelease({preview, confirmed?})` returns deterministic, escaped, self-contained HTML. Without confirmed metadata it is watermarked **REVIEW DRAFT**. Confirmed exports must use a fresh `read_record_release` result. Ineligible/event-bearing copies are marked **INVALIDATED RELEASE** and prohibit delivery. Certificates use the existing frozen certificate renderer. The original attachment manifest lists filenames, MIME and sizes; private Storage paths and file bytes are not placed in the exported HTML. No PDF or attachment download is implied.

`RecordReleaseArtifact({artifact, refreshConfirmed?})` displays the HTML in a sandboxed iframe and its **Save review HTML** button downloads those actual HTML bytes. It provides no confirmation, sender, raw-document download, or provider call. Confirmed exports require `refreshConfirmed` and fail closed without it. The panel supplies a fresh server read immediately before generating the HTML download; later delivery integration remains separate. A field named `eligible` must never be treated as a live guarantee after the underlying RPC response becomes stale.

Validation covers signed-only and same-patient boundaries, private content exclusion, explicit lab report selection, frozen size/MIME, recipient matching, clinical gate, snapshot/hash conflicts, UUID/actor retries, corrections/voids, withdrawal, RLS/audit, HTML injection, certificate snapshot composition, the sandboxed review component, and an actual HTML download.

## Patient selection and confirmation panel

`PatientRecordReleases({petId, onDirtyChange?})` lists eligible source families, household contact choices, and paginated confirmed packages. `list_record_release_sources(p_pet_id, p_offset)` returns up to 100 entries per family plus household contacts and form-acceptance status. The source-page controls retain selections across pages. “Select all shown” selects only the visible source page; exceeding the per-family bound rejects the operation without silently truncating it. The separate **Select all eligible records across every page** action uses `select_all_record_release_sources(p_pet_id)` to collect all twelve families in one SQL statement snapshot, independent of the visible page. It returns `{selection, excluded_unavailable_originals, excluded_labs_without_shareable_original, scope}`. Any family above 100 fails the entire request with a split-package instruction; no partial selection replaces the current selection. Missing original objects and labs without an eligible shareable original are counted explicitly. Unsigned drafts, invalid certificates, and internal originals remain ineligible. The selected IDs are fixed at collection time; the subsequent preview freezes their complete contents. Later records are not silently added to that reviewed package. This does not claim that unimported external records exist in the system.

Selection and recipient controls lock after preview. Editing clears review, and confirmation uses the exact preview arguments, snapshot and SHA-256 returned by the server. A lost/ambiguous response retains the request UUID and original payload; a definitive stale response requires a fresh preview. The review checkbox explicitly covers structured contents, original attachments, and the household recipient. Original files can be reviewed separately; the HTML never pretends to embed their bytes. Confirmed packages can be reopened, status-refreshed for actual HTML export, or withdrawn with a reason. No email/SMS transport or arbitrary recipient entry is available.

The component registers browser unload protection and contributes to the existing shared SPA dirty-state guard through `onDirtyChange`; it does not register a competing router blocker. The scoped patient-panel mount passes that callback. Form-schema acceptance remains operator-only, and messaging attachment authorization remains a later server-side integration.

## Diagnosis, allergy, weight, and treatment disclosure

- `problem_ids` selects current active **and resolved** diagnoses with all available clinical revision evidence projected from the existing audit trail. Title, onset, status, priority, clinical notes, author, and dated before/after revisions are retained. Raw audit data and unrelated records are never returned. Missing pre-system revision history is not reconstructed. High-priority diagnoses use readable red and the explicit word **IMPORTANT**, including historical revisions.
- `patient_summary_ids` contains this patient ID and freezes existing allergy text, profile version and legacy weight. Empty allergy text explicitly does not establish absence of allergies. The legacy weight is labeled as having an unknown measurement date; it is not converted into a fabricated dated measurement.
- `weight_ids` selects individual immutable measurements with units, measured date, recording author and recording time.
- `treatment_ids` selects medication and vaccine administrations/dispenses, including corrected entries. Frozen product/manufacturer/lot/expiry/dose/route/site/veterinarian/license, recorded due date, source provenance and authorship are preserved. Corrections retain their reason, date, author and replacement record reference. Corrected entries are explicitly historical and do not imply a current administration or due date. No due date is recomputed. Billing IDs and retry payloads are excluded.

Clinical notes, including diagnosis revisions and treatment provenance, are disclosed as authored when their source is selected. These are medical history, not categorically omitted workflow notes. Staff must review the actual complete artifact and selected originals; there is no automatic redaction or inference about what prose may be sensitive. New diagnosis revisions, treatment corrections, and changed patient allergy/profile fields invalidate already confirmed packages without mutating their saved contents. Newly created records that were never selected do not silently expand historical packages.
