# Server-only worker authentication

`dispatch-outbox`, `process-inbound`, and `queue-reminders` accept a managed secret API key in the `apikey` header. Their gateway `verify_jwt` setting is false because modern secret keys are not JWTs. The shared `authenticateWorker` handler validates the entire `SUPABASE_SECRET_KEYS` JSON object and matches the supplied key exactly against a configured named secret. It returns that trusted matched key for the database client. Arrays, missing/empty maps, malformed JSON, non-string entries and non-secret entries fail closed.

An explicitly supplied API key (including an empty or unknown one) cannot fall back to Authorization. For callers without an apikey header, the existing exact `Authorization: Bearer <managed SUPABASE_SERVICE_ROLE_KEY>` comparison remains for legacy compatibility. It does not accept an independently issued JWT based on decoded claims, role text, or an unverified signature. Use managed secret apikeys for new worker invocations; publishable/anonymous keys and user sessions cannot invoke these workers.

Deploy these three handlers together with their new gateway settings. Changing a gateway flag alone does not grant access, but the updated handler is required to support modern keys. Keep worker credentials server-side. The code never logs or returns credentials. Staff JWT endpoints, webhook verification, queue authorization, delivery suppression and runtime disable controls are unchanged.

Tests execute all three entrypoint handlers with injected database/work functions to verify unauthorized calls perform neither. They cover exact named keys, unknown/blank/publishable values, malformed maps, header precedence, legacy compatibility and the matched database credential. Hosted commissioning is a separate operator step: first confirm outbound/scheduling are disabled and inbound work is empty before probing with a managed secret. This change performs no deployment or live worker calls.

This uses the minimal managed-environment option described by [Supabase's key migration guide](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys), with the service-call header and gateway settings described in [function authentication](https://supabase.com/docs/guides/functions/auth) and [authorization headers](https://supabase.com/docs/guides/functions/auth-headers). It avoids adding a new SDK dependency to existing handlers.
