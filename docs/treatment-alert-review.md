# Exact patient alert review before a new treatment

`read_patient_treatment_alerts(p_pet_id)` is restricted to active authenticated staff. It returns `{snapshot, source_hash}`. The snapshot includes schema version1, patient ID/version, every high-importance problem (including resolved history), authored notes/status/version, and the legacy allergy text with an explicit statement that original clinician/date/verification are not established. Empty history does not establish absence of allergies. The query is not paginated or silently truncated; a snapshot over1MiB fails visibly.

A **new nonhistorical** `record_patient_treatment(p_id,p_request)` requires `p_request.alert_review = {source_hash, acknowledged:true}`. No caller-supplied reviewer identity/time is accepted. The procedure reads and compares current content before any new inventory or invoice mutation. On success it atomically records an immutable `treatment_alert_reviews` association with the exact snapshot/hash and session actor/time. Direct table writes are denied; active staff can read the audit association. Existing successful exact-ID/request retries return the original treatment before comparing later alerts, preserving response-loss recovery without another stock debit, charge or acknowledgment row. A different actor or changed request cannot replay the original operation.

Historical source transcription remains non-billing/non-stock and requires no current-care acknowledgment. It rejects an `alert_review` field rather than fabricating review of past care. Existing treatment records are not backfilled with pretend approvals. This internal workflow audit is separate from client medical-record release forms; no release schema or previously confirmed export changes here.

Shared patient-row locks serialize treatment alert validation against relevant problem writes and all patient profile updates, including allergy text. The patient version intentionally makes unrelated identity edits invalidate an uncommitted review conservatively. Problem and patient form saves invalidate the shared `patient-problems` query prefix, refreshing treatment and booking snapshots. The checkbox binds to its displayed hash, so changed content clears its effective acknowledgment. A definitive stale-hash40001 rejection preserves form fields, discards the rejected operation and refreshes alerts for a new explicit acknowledgment/request; ambiguous outcomes still retain the original UUID/payload for exact retry. Alert read/decoding failures show a local reload control and block new care. No clinical recommendations are generated.

Validation includes direct RPC bypass, false acknowledgment, exact actor stamping, inactive/anonymous/service denial, immutable audit rows, changed critical/resolved history, legacy allergy changes, stock/billing rollback, historical transcription and idempotent committed retries. Existing inventory/certificate fixtures now explicitly acknowledge their synthetic current snapshots before new care.

Run `python3 tests/clinical/verify-alert-locks.py` against the isolated local `supabase_db_livingroom-vet-foundation` container for a reproducible two-session lock check. It creates a disposable schema-only database, verifies both a problem write and an allergy write wait on an active snapshot lock, then proves each committed change rejects the old treatment request without stock/billing writes. Its synthetic records are never written to the application database and the disposable database is removed in `finally`. No providers are contacted.

The database CI job runs this same two-session script after `supabase test db`, deriving the exact container from `supabase/config.toml` with `--project-config`. For another explicitly isolated local container, set `TREATMENT_ALERT_TEST_CONTAINER`. This verifies database snapshot locking and subsequent stale-RPC rejection, not provider or network concurrency.
