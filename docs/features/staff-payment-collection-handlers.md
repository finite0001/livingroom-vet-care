# Staff payment collection preparation and recovery

`prepare-payment-collection` and `recover-payment-collection` are authenticated staff Edge endpoints. They return a safe, actor-owned grant envelope for review. They do not return usable collection/status capabilities or payment URLs, call Stripe, attest a review, or enqueue delivery.

Both endpoints are disabled unless `PAYMENT_ACCESS_STAFF_ENABLED=true` and `APP_URL` is a trusted exact origin. They retain platform JWT verification and authenticate the bearer user before using actor-scoped RPCs. A supplied mismatched Origin is rejected. Responses use `no-store, private` and `no-referrer`. This staff flag is independent of the public collection/status flags, so a practice can prepare drafts before public payment access is enabled.

Preparation accepts exactly `p_request_id`, `p_invoice_id`, `p_client_id`, `p_source_hash`, numeric integer `p_amount_cents` (50–99,999,999), and `p_expires_at`. The request UUID and all arguments must remain stable across retries. SQL remains authoritative for source eligibility, ownership, balance and expiration. Existing captures are returned only after the actor prepare RPC validates the exact original arguments. A rejected changed-argument request cannot become a successful recovery response.

Recovery accepts `p_invoice_id` and an optional `p_request_id`, and runs before key selection. It returns the original safe metadata or null, even when the original signing key has been removed or the active version/origin has changed. It neither renews expiration nor reconstructs capabilities. Captured, reviewed and revoked grants stay inspectable subject to SQL actor authorization.

Only an uncaptured preparation needs `PAYMENT_ACCESS_ORIGIN`, `PAYMENT_ACCESS_ACTIVE_KEY_VERSION` and `PAYMENT_ACCESS_KEYS`. A brand-new draft is not created when this configuration is missing. Service capture obtains the canonical SQL context, validates its identity and digest, derives domain-separated capabilities in memory, and persists only their hashes. It then confirms the capture through actor recovery. A lost capture acknowledgement can return the original confirmed capture; otherwise HTTP 202 preserves the request UUID and explicitly requires recovery. No replacement request or new expiration is invented.

The envelope projects grant, canonical capture context/digest, event identifiers/kinds/context digests, and attempt identifiers/states. It excludes token hashes, arbitrary additional fields, freeform revocation reasons, and delivery receipts. Canonical context accepts only the immutable payment grant fields, preventing extra capability-bearing data from being forwarded. `attest_payment_collection` remains a separate explicit staff operation for the future review interface.

Validation: focused mock-RPC tests cover exact actor/service boundaries, disabled and missing configuration, immutable retries, lost acknowledgements, removed-key recovery, cross-actor denial, strict inputs, safe projection and altered canonical contexts. Frozen Deno checking validates both actual entrypoints. These checks do not provision keys, deploy endpoints, send messages, or collect payments.
