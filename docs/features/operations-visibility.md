# Administrator operations visibility

`/hub/admin/operations` is available through desktop and mobile administrator navigation. Active administrators can observe safe counts, outgoing work, scheduler candidates, blocked reminder handoffs and recorded scheduler runs. Each section loads independently and clears its previous observation before refresh; a section failure cannot imply that its old data is current. Account changes unmount all actor-specific observations. This page calls read-only discovery RPCs only.

Observation times and oldest timestamps are evidence, not an invented alert threshold. An empty queue does not establish provider readiness, worker activation or scheduling health. No recorded scheduler run is explicitly unknown. Started runs retain unknown outcome and counts; completed receipts show validated queue counts without claiming provider dispatch. Run references identify unresolved evidence for operators.

Outgoing rows link to their actual conversation and, when available, household billing. Billing links open the household, not an automatically selected invoice. Provider acceptance is distinct from recipient delivery. Existing unmatched-sender and incoming-processing screens retain their own review and recovery authority; no generic send retry is introduced.

Blocked rows show stable job/source references and link to the source patient where available; schedule and policy links are explicitly general navigation, not a claim that an old job is selected. Candidate rows include care sources whose jobs have not yet been created. They are eligible for scheduler consideration, with final source/recipient checks still required. Keyset cursors use exactly the returned timestamp, ID, kind or opaque candidate key; browser clocks do not reconstruct them. Pages are bounded and do not promise a frozen snapshot across concurrent work.

The existing administrator Stripe retry panel uses the additive `read_stripe_event_queue_page` discovery, defaults to unfinished work, supports explicit states and reaches older notifications. Paging is disabled while a review is open or an original retry awaits recovery. Closing a review permits paging; retry UUID/hash/reason storage and receipt-first recovery remain unchanged. The operations page itself links to that existing workflow and never requests a retry.

Validation: operations parsers reject private/raw-error projections and contradictory scheduler evidence; cursor tests preserve SQL timestamp precision. Mocked browser checks cover independent failure, exact keyset pagination, correct internal links, no observation mutations, ordinary-staff denial and older unfinished Stripe preview. Existing before/after lost-acknowledgment Stripe retry regressions remain passing. Hosted deployment, cron activation and actual provider transport are separate commissioning work.
