# Payment handler factories

Status: shared handlers and four Edge entry points are implemented locally; none is deployed or commissioned. They require payment ledger3000, durable inbox3100 and reconciliation observations3300. Actual Stripe sandbox acceptance remains required.

- `stripe-checkout.ts` authenticates staff, resolves the immutable actor-scoped ledger context, retrieves an already-known Checkout Session and only creates when the original prepared request remains eligible. It saves normalized evidence before returning a transient checkout URL. Failed save acknowledgements return an uncertain result retaining the request UUID. Expiry always retrieves the authoritative session after the provider attempt, including when expiry loses a race to payment. Paid/expired ledger contexts cannot create another collection.
- `stripe-webhook.ts` verifies the exact raw-body signature before storage, keeps a SHA-256 fingerprint and small typed event envelope, and acknowledges only after the receipt callback succeeds. Account/mode/API-version mismatches, unattributed payment objects and external financial adjustments enter review. Unrelated event types are ignored durably. Neither full customer payloads nor checkout URLs are saved in the receipt.
- `stripe-event-worker.ts` processes one leased event, retrieves current provider objects rather than trusting event order, and completes through the inbox's atomic ledger-evidence/lease transaction. Provider outages retry; lost completion acknowledgements await lease recovery. Provider context mismatches enter review without applying money. The provider-context RPCs intentionally work independently of the originating staff member's current active status.

`stripe-runtime.ts` wires the callbacks to service-only RPCs. `invoice-checkout` and `invoice-refund` require gateway JWT verification and explicit Auth user/active staff context. `stripe-webhook` verifies provider signatures. `process-stripe-events` validates exact managed or legacy worker credentials before work. All RPC errors are propagated without logging provider payloads or credentials.

`STRIPE_PAYMENTS_ENABLED` enables provider operations. `STRIPE_COLLECTIONS_ENABLED` and `STRIPE_REFUNDS_ENABLED` independently permit new immutable requests to reach Stripe; known-session/refund recovery remains available when those switches are off. `STRIPE_WEBHOOK_ENABLED` controls receipt and `STRIPE_EVENT_PROCESSING_ENABLED` controls workers. Every switch defaults off. `STRIPE_WEBHOOK_SECRET`, exact `STRIPE_ACCOUNT_ID`/`STRIPE_LIVEMODE`, pinned endpoint API version, `STRIPE_SECRET_KEY`, trusted `STRIPE_RETURN_ORIGIN` and staff `APP_URL` must be commissioned deliberately. Missing configuration cannot silently select an account or mode.

The refund endpoint requires an already reserved, actor-scoped refund request. Known refunds are retrieved; paused creation does not prevent recovery. Malformed responses record a bounded reconciliation observation rather than inventing a provider ID or settled amount. Ledger reservations remain in place until authoritative evidence and review resolve uncertainty.

Validation: 41 combined payment-focused tests pass, covering the provider boundary plus staff authentication, exact request recovery, lost persistence acknowledgements, expiry/payment races, webhook forgery and receipt failures, out-of-order event reconciliation and leased-worker completion failures. All four Edge entry points pass frozen Deno type checking. The local runtime harness additionally passed 18 actual HTTP/Auth/PostgREST assertions with Deno network access restricted to localhost: disabled routes, invalid JWTs, exact worker authentication, empty queue, forged signatures, durable signed receipt/hash/deduplication, quarantine and exact synthetic cleanup. No provider calls, emails or SMS were sent by these tests.
